# apps/daily — daily.lab115.com

每天 LA 时间早上 7:00 抓一遍订阅的博客，用 DeepSeek 提炼中文观点摘要，
生成一张适合截图分享的竖版长图页面，同时把当天结果以 JSON 提交到
[`github.com/imnaifu/files`](https://github.com/imnaifu/files)。

**网站和 worker 是同一个容器**：Next.js 服务页面，`src/instrumentation.ts` 在
服务器启动时注册 `node-cron`。数据不进数据库 —— 那个 git 仓库就是存储层，容器把
它 clone 到挂载卷上，页面直接读本地磁盘上的 JSON。

```
每天 07:00 (America/Los_Angeles)
  ↓
git pull ──→ 当天已有就退出 ──→ 拉全部源，筛出过去 24h 的文章 ──→ 按 URL 去重
  ↓
取正文（RSS 全文 / 抓原文页）
  ↓
每篇两次 LLM 调用：① 只打分  ② 过了门槛的才写摘要 + 分类
  ↓
按分数过门槛 ──→ 按分类排序，每篇一张卡 ──→ 写 JSON ──→ git commit & push ──→ Bark
```

## 配置：`config.json`

**所有需要人工决策的东西都在 `apps/daily/config.json` 里**，改它不用碰 TypeScript：

- `sources` —— 订阅哪些博客（url、名称、配色、摄入上限、抓取方式）
- `categories` —— 分几栏、每栏叫什么、边界怎么划
- `fallbackCategory` —— 分不出来时落到哪一栏
- `publishMinScore` —— 唯一一道分数门槛：低于它就不发布

和 `src/lib/config.ts` 的分工：**编辑决策进 `config.json`，运维参数进环境变量**
（密钥、cron、时区、时间窗口）。

它是被 `import` 进来的、打进镜像的，所以改完要 push 并重新部署才生效。

`src/lib/user-config.ts` 在加载时校验，写坏了会**当场抛出可读的错误**，而不是静默
丢掉一条：一个悄悄消失的源看起来和一个停更的博客一模一样，那种 bug 能藏几个月。

```
config.json: source "heavybit" has neither a feed nor a scrape config
config.json: duplicate source id "heavybit"
config.json: fallbackCategory "nope" is not one of the categories — ...
config.json: source "alienchow" scrape.pattern is not a valid regex: ...
config.json: source "alienchow" scrape.flags must include "g"
```

正则在 JSON 里存成 `pattern` + `flags` 两个字符串，加载时编译成 `RegExp`。

几个需要知道的：

- **Hacker News 走 hnrss.org 而不是官方 `/rss`**，因为只有第三方服务能按分数过滤，
  而没过滤的首页在这堆博客旁边基本是噪声。它的条目指向任意第三方站点，正文靠抓那些
  页面 —— 付费墙、纯 JS 页、PDF 都可能抓不到，这时正文为空，模型只看标题。
- **HN 的门槛从 200 分提到 300、`maxPerRun` 从 10 降到 5**，因为它一个源就占了整天的
  40%（8-12 是 24 篇里的 10 篇），而占的位置几乎全是两类东西：单库/单芯片的工程内幕
  （`Spaghettifying DRAM`、`Why tiny JPEGs look different in Chrome`）和版本发布公告
  （`Grok 4.6`、`Qwen3.8-2.4T`、`DeepSeek V4 Pro 0813`）。**HN 的分数和 geek 程度是
  正相关的**，所以调 feed 参数只能减量、减不了偏 —— 真正治它的是打分那一节的第二道
  测试加上 `publishMinScore`。
- **Heavybit 订的是 `/library/blog/feed`，不是 `/library/feed`。** 全站 feed 里 1449 条
  有 771 条是播客单集（53%），只带 ~500 字符 show notes，摘出来的必然是空话。栏目 feed
  415 条、播客 0 条、正文 7k~17k。代价是频率从 3.4 天/篇降到 11 天/篇 —— 少的正是那些
  没有文字内容的条目。
- **Uncharted Territories 的 "Dispatch" 系列是付费内容**，feed 只给 ~400 字符预览，
  抓原文页拿到的还是预览。**Slow Boring 有一半条目同样是付费预览**，Lenny's 约 3/20。
  这类源留着仍有价值（免费文是全文），但预期里就该有一部分只能凭标题和导语摘要。
- **Nic Chan 自 2026-02-10 停更**。留着不花成本 —— 没有新文章的源在页面上只是一个
  计数为 0 的 chip。
- **有些 feed 双重转义自己的正文**（`jacob.gold` 的 description 是
  `&lt;p&gt;US residential…`）。所以 `stripHtml()` 去标签跑两遍：解码实体这一步会
  *产生* 原本不存在的标签，只跑一遍会把字面量 `<p>` 喂给模型。
- **ByteCode.News 和 Jake Gold 都是原创博客**，虽然标题常引用别人（`Bjarnason: …`）。
  两者 feed 里的链接 100% 指向自己站内，所以抓正文抓的是它们自己的页面，不是第三方。

  因为稿在播放器组件里或另一个 URL 上）；**带稿但有杂质的**（Latent Space 约一半是
  `[AINews]` 每日链接汇总，正是 substance 1-2 档点名的 "selection only"；Sinica 混着
  "Phrase of the Week" 这类短条目）；**带稿但停更的**（Cognitive Revolution 914 天、
  patio11 的 Complex Systems 594 天）。
- **Tim Ferriss 是「同一期发两次」的样本，去重挡不住它。** 每期在 feed 里出现两条：show
  notes（~8k）和 `The Tim Ferriss Show Transcripts: …`（~50k），URL 不同、隔 2 天发。
  `idOf(url)` 按 URL 去重，两条都会活下来，而且因为隔了 2 天，24 小时窗口会让它们落在
  不同的日期上 —— 表现成隔天重复发同一期，看起来完全不像去重的锅。收它要先按标题前缀过滤，
  那是给一个源开特例，所以没收。
- **Conversations with Tyler 想收但拿不到，卡在正文抽取上。** 主 feed `/feed/` 是空的
  （947 字节、0 条 item），`/episodes/feed/` 有条目但 `description` 全空。稿在网页上，而
  `fetchPage()` 的「先 `<article>` 后 `<main>`」在它的页面上命中的是一张「相关单集」卡片，
  实测整页抓下来只有 **24 个字符**（`Episode 233 Ross Douthat`）。这是 `<article>` 优先
  这个启发式的已知失败形态：页面里有多个 `<article>` 而正文不在第一个里。
- **Derek Lowe 的 In the Pipeline 和 Nature 订不了，原因在解析器不在源。** 它们发的是
  RSS 1.0（`rdf:RDF`），而 `parseFeed` 只认 `rss.channel.item` / `feed.entry` /
  `channel.item`，条目挂在 `rdf:RDF.item` 上取不到。要订这类得先加一个分支 —— 记在这里
  是因为它看起来会像「那个源抓不到东西」，而不是「少写了一行」。
- **Reddit 和聚合站测过，只有一种子版块能用，最后一个都没加。** 帖子页是纯 JS 渲染，
  抓下来 `stripHtml()` 后只剩 6 个字符（`"Reddit"`），所以**正文只能来自 RSS 的
  self-text，评论区拿不到** —— r/AskHistorians 那种「答案在评论里」的版块摘出来会是
  一个提问，r/books 那种外链贴正文只有 460 字符。唯一合格的是 r/HobbyDrama（全文
  中位 30k）。另外 Reddit 对连发请求 429 得很快：并发探 7 个版块中 6 个失败，间隔
  4 秒仍然失败，单发才正常。同一批还测掉了 Lobsters（正文中位 **8** 字符，且选题是
  HN 的子集）、MetaFilter（feed 只覆盖 **0.4 天**，违反下面那条 `feed 条数 ÷ 日产量
  > 1 天`）、Kottke 和 Longreads（正文是推荐语不是文章，中位 224 / 1266）。
  **聚合站的通病是正文在第三方站上** —— 那正是 HN 走的路，再加一个只是复制它的失败模式。
- **Dan Luu 和 Damodaran 的正文最长，中位 63k 和 33k。** 加它们的时候 `BODY_CHAR_LIMIT`
  还是 20000，所以只喂得进前三分之一到三分之二；量了一遍发现被截的远不止这两个源，
  于是把上限提到 80000（见下面「正文预算」那节），现在两者都能整篇喂进去。
- **XDA · AI Tools 设了 `maxPerRun: 3`**（原本不限）。它 5.9 篇/天、只给导语、每篇都要
  抓原文页，是成本最高的源，而产出是清单体 —— `Google recommends these 7 NotebookLM
  prompts` 45 分、`I can't believe how good this AI coding model is` 55 分。加了三个
  真正做 AI 分析的源之后没有直接撤掉它，是想让分数来决定；限量先把成本压住。

### 没有 feed 的源怎么办

`Source.scrape` 是给完全没有 RSS 的站点准备的（目前只有 alienchow.dev）：给一个列表
页地址和一个带 `url` / `date` / `title` 命名组的全局正则，`parseListing()` 会把它变成
和 feed 完全一样的候选项，后面的流程不用区分两者。

用正则而不是 DOM 库，是因为要解析的列表页就是一串扁平 anchor，而这个文件本来就在用
正则读 HTML。**如果哪天某个站点需要真正的 DOM 遍历，那是该引入解析器的信号，
而不是把正则堆得更复杂。**（alienchow 的 HTML 是压缩过的，属性值不带引号，
正则要能吃 `href=/post/slug/` 这种写法。）

两个关键取舍，改源之前先读一下：

- **不订 XDA 全站 feed。** 全站每天发 ~69 篇但 feed 只保留 10 条（约 3.5 小时），
  一天抓一次会丢掉 95%。分类 feed 每天只有几篇，10 条足够覆盖 24 小时以上。
  加新源时按这个标准检查：`feed 条数 ÷ 日产量 > 1 天` 才安全。
- **正文不一定在 feed 里。** XDA 的 `content:encoded` 只有 90~270 字符的导语，
  caolan.uk 的 Atom 条目连摘要都没有 —— 这两个源标了 `fetchBody: true`。任何源的
  正文短于 `SHORT_BODY_CHARS`（1200）也会自动去抓原文页。
- **正文抓取有并发上限**（`BODY_FETCH_CONCURRENCY`，6）。原来是无上限的
  `Promise.all` —— 在全是已知博客时没问题，但 HN 指向任意第三方站点，任何一个都能
  占住 socket 直到 30 秒超时，窗口一宽就是几百个并发连接。加上限后最坏耗时被约束在
  `ceil(文章数 / 6) × 超时`。
- **正文短于 `MIN_USEFUL_BODY`（200 字符）视为没有正文。** HN 的 feed body 是
  ~150 字符的「Article URL … Points: 257」样板文字，拿它去摘要等于凭空编一篇文章；
  留空反而会让 prompt 说「只看标题判断」，那是诚实的。
- **长文源要留够正文预算。** `BODY_CHAR_LIMIT` 默认 **80000** 字符。它最初是 6000，
  那是按 XDA 短文校准的；neciudan.dev 这类 28k~74k 字符的长文在 6000 下只会喂进
  前 8%，摘出来的是引言而不是论点。输入侧便宜（$0.14/M，上下文以十万计），值得给足。
  为什么从 20000 又提到 80000，见下面「正文预算」那节 —— 20000 截掉的比看起来多得多。

## 两个 cron，不是一个

| | 频率 | 做什么 |
|---|---|---|
| `DAILY_CRON` | 默认每天 07:00 | 拉取 → **当天已有就跳过** → 抓取 + 摘要 + commit + push |
| `DAILY_SYNC_CRON` | 默认每小时的 7/22/37/52 分 | **只 `git pull`**，不调模型、不 commit |

两者的分钟必须错开。两个 cron 共用 `jobs/daily.ts` 里的同一把锁，而抢不到锁时的行为是不对称的：sync 安静跳过（15 分钟后还有下一次），daily 直接抛错（下一次是 24 小时后）。所以 sync 不能落在整点 —— 否则它会先拿到锁，把当天的 digest 挤掉。改 `DAILY_CRON` 时记得同步挪开 `DAILY_SYNC_CRON`。

定时任务带 `skipIfPublished`：仓库里已经有当天的 digest 就直接退出，不抓取也不调模型。
因为那一天可能已经在别处生成过（笔记本手动跑、上一个容器实例），重跑等于为同一天付两次
模型钱、还会覆盖已发布的内容。

**这个检查必须放在 `ensureRepo()` 之后**，这是它唯一容易写错的地方：落后于 origin 的
clone 会把「今天」看成不存在，于是重新生成一个上游早就有的日期。

手动 `npm run once` **不带**这个开关 —— 手动重跑本来就是这个入口的用途。想要定时任务
那种行为就加 `npm run once -- --skip-if-published`。

第二个是必需的，不是优化。页面读的是容器里那份 clone，而 clone 原本只在**容器启动时**
和**每日任务运行时**才会前进 —— 从别处推上去的 digest（笔记本手动跑、补数据）在下一个
07:00 之前对站点完全不可见。实际后果是：本地推了三次、远端明明有内容，线上仍然显示
「今日无更新」。

两者共用同一把锁（`jobs/daily.ts` 里的 `running`），因为它们操作同一个工作树，
fetch 撞进 rebase 中间会把它弄坏。每日任务在跑时，同步会直接跳过。

## 网络失败怎么办

GitHub over HTTPS 会偶发超时。这是个无人值守的每日任务，而且**没有跨天去重**，
所以一次抖动丢掉的那天是永久性的 —— `repo.ts` 因此对网络操作做了这些事：

- **clone / fetch / push 都重试 4 次**，退避 5s → 15s → 45s
- 传输速率低于 1KB/s 持续 30s 就中断（`http.lowSpeedLimit`），而不是挂到 socket 超时
- **fetch 失败不致命**：只要本地已有 clone，就用本地状态继续出图，下次再同步。
  只有「没有 clone 且 clone 不上」才会让整个任务失败
- **push 失败不致命**：内容已经 commit 在本地，下次运行会带上去

最后一条依赖 `syncToOrigin()` 的一个关键行为：本地有未推送的 commit 时走
**rebase 而不是 `reset --hard`**。早期版本无条件 hard reset（当时假设 push 永远成功），
一旦 push 失败，那天的 digest 会在下次运行时被静默抹掉，且没有任何东西能重新生成它。

走代理的话 `git` 会自动读 `HTTPS_PROXY` / `https_proxy`（`repo.ts` 把整个
`process.env` 透传给子进程），不需要改代码。

## 分类

`config.json` 的 `categories` 是**唯一**要改的地方：模型的 enum、分类说明和页面栏目
顺序全部由它生成。加一类就是往数组里加一项。

目前 8 类：技术 · 商业 · 投资 · 经济 · 科学 · 设计 · 生活 · 人文。**AI 不是单独一栏** ——
它和软硬件的手艺合并进了 `技术`，`hint` 里写明了这一点。每栏内的文章全部出卡片，
没有数量上限（`categories[].cardCount` 已删）。空分类不渲染，所以一天通常只出现 5~6 栏。

**为什么从 5 类拆到 9 类。** 兜底类会吸干一切：实测两天，`人文` 各拿到 11 篇
（占 24 篇的 46%、17 篇的 65%），而里面装的其实是四种完全不同的东西 ——
移民收入同化和 Medicare for All（政策）、夜间咖啡因和什么让人快乐（研究）、
删掉日历链接（个人工作方式）、Fast Company 谈新美学（设计）。**兜底类满了不是分类
错了，是分类不够。** 于是拆出 `经济` `科学` `设计` `生活`，`人文` 退回它本来的位置：
历史、哲学、宗教、语言、媒体与网络文化、讣告。

顺带把 `投资` 的边界放宽了一点 —— 它两天都是 0 篇，而 `Mistakes in financial
economics` 被扔进了人文。现在 hint 明确收「金融理论及其失败」，同时把劳动市场、
贸易、公共支出让给 `经济`。

**分类是逐篇由模型判断的，不是按源固定映射。** Hacker News 和 Marginal Revolution
本身就横跨从数据库内核到劳动经济学，按源写死会大面积错分。

`hint` 字段直接进 prompt，**要写成边界而不是主题清单** —— 难的从来不是「什么是 AI」，
而是「为什么归这里而不是隔壁」。实测教训：兜底类最初写成「其余一切值得读的：社会、
经济、历史、科学…」，结果把 `What sort of maths are LLMs good at?` 当成「科学」吸走了。
现在它显式让位（`LAST RESORT — use only when none of the categories above fits`），
prompt 里也加了「永远选最具体的那一类」。

**类别越多，让位就越要写死。** 9 类里相邻的边界很多（经济↔投资↔商业、科学↔技术、
生活↔科学↔人文），所以每条 hint 结尾都点名把什么交给谁：「关于劳动市场的论文是
`经济`，芯片制程是`技术`」。只写自己收什么、不写自己不收什么的 hint，等于把判断留给
模型的直觉，而直觉在批次之间是漂的。

模型没给或给了未知值时落到 `FALLBACK_CATEGORY`。旧 digest 里的类别若已被删除，
`categoryOf()` 也不会抛错 —— 归档页必须永远能渲染。

边界模糊的文章在不同批次间会漂移（`AI is removing the middle class of software
engineering` 有时判成商业、有时人文），这是模型判断的正常方差，不是 bug。

## 交互

- **英文回来了，语言切换器也跟着回来了。** `summary.en` 是可选字段，`/en` 渲染它，
  没有它就回落到中文 —— 回落有两种正常情况：英文半边恢复之前写的归档 digest，以及
  某一跑里中文回来了、英文没回来的那一篇（见下面「英文那一半」）。切换器
  （`Shell.tsx` 的 `LangSwitch`）那行 `return null` 已经删掉。

  **每个渲染方都走 `summaryFor`（`lib/take.ts`）**，不再各自去拿 `summary.zh`：
  「英文缺了怎么办」这条规则有且只有一个答案，而它以前散在六个组件里。

- **只有分类 tab，没有「全部」。** 散文摘要太长、每篇又都是整张卡片，整页平铺根本读不完，
  所以「全部」实际上没人会用。默认停在第一个分类（`groups[0]`）。
  这里曾经要找「第一个真正**有卡片**的分类」，因为某天 AI 栏可能全是版本发布、分数集体
  低于卡片门槛，一打开就是一列光秃秃的链接。低分文章不再进页面之后，存在的栏必然有
  卡片，那次搜索已经没有东西可找。

- **没有头条位。** 排名第一的文章曾经被抽出来做一张大卡片放在 tab 上方。删掉它是因为
  **它站在分类系统之外**：tab 够不着它，于是需要一个「全部」tab 才能让它和其他文章一起
  出现，而「全部」本身又是没人用的。现在所有文章都在自己的分类里，`groups` 覆盖全部
  —— 报头的篇数和各 tab 计数之和因此严格相等（实测 15 = 5+2+6+1+1）。

- **语言开关曾经在 tab 上面**，位置比 tab 更高一层，因为它重写的是下面每一张卡片而不只是
  当前那一栏。现在它 `return null`，见上面那条。

- **下拉刷新（`PullToRefresh.tsx`）。** 这个手势是**为装成 App 之后准备的**：浏览器标签页里
  有刷新按钮、也有系统自带的下拉，而 standalone 窗口两样都没有，偏偏这个站的内容每天早上
  换一次 —— 没有它，昨天打开过 App 的读者想看今天这期，只能把窗口关掉重开。

  几条边界条件都是有理由的，改之前先读一遍：

  - **只在触屏上挂监听**（`(pointer: coarse)`），桌面上一个 listener 都不注册。判据是输入
    设备而不是 OS 名字：能不能下拉取决于有没有手指。
  - **`<html>` 上加了 `overscroll-y-contain`**（在 `layout.tsx`，不在 `index.css` —— 那个
    文件只放 token）。这一条是前提而不是装饰：Chrome Android 自带下拉刷新，iOS 会把整个
    文档橡皮筋，连 `fixed` 的指示器一起往下带 —— 那就变成两个指示器互相打架。
  - **只有从页面最顶端（`scrollY <= 0`）、单指、且当前没有 `dialog[open]` 才起手。** 分享面板
    是个 `<dialog>`，里面自己会滚，在它上面下拉刷新会把正要去点「保存图片」的读者的页面
    换掉。
  - **确认是「明显向下」之后才接管手势**（`dy` 要压过 `dx`），然后才 `preventDefault` ——
    所以 listener 必须是非 passive 的。分类 tab 那一排是横向滑的，这一条就是为它留的。
  - **阻尼 0.6、阈值 56px**，所以真正要拉动的手指距离是 100px 上下。这个数是故意超过随手
    一划能到的范围的：这个手势会把眼前这一页扔掉重新跟服务端要一份，误触的代价比多拉
    一次大。
  - **刷新走 `router.refresh()`，不是 `location.reload()`。** 每个页面都是 `force-dynamic`，
    软刷新重跑一遍服务端组件就够了：不白屏、不跳滚动位置、字体和 bundle 都不重新下载。整页
    reload 四件事全犯，慢手机上那就是整个手势的手感差别。
  - **spinner 有 600ms 的最短显示时间和 8s 的兜底超时。** 前者是因为热的 `router.refresh()`
    能在一百毫秒内回来，一闪而过的 spinner 读起来像出了故障而不像干完了活；后者是因为
    `router.refresh()` 不返回 promise 也不会 reject —— 断网时它不是失败，是永远不到，
    `isPending` 就一直是 true。

- **「存成 App」（`InstallApp.tsx` + `lib/install.ts`）。** PWA 的地基本来就齐了（每种语言
  一份 manifest、带 `fetch` handler 的 `sw.js`、三个尺寸的图标、iOS 那两个 meta），缺的只是
  一个入口和一段说明。

  - **一个按钮后面是两件不同的事。** Chrome / Edge 会发 `beforeinstallprompt`，那就有一个
    真正的一键安装可以给；Safari（iOS 和 macOS 都一样）什么都不发、也没有任何 API，安装
    就是一个要读者自己去菜单里找的选项，那么唯一能做的事就是说清楚是哪个菜单、那一项叫
    什么。面板同时提供两者：有原生按钮时放在最上面，分步说明**照样留着** —— 那个 offer 被
    拒绝过一次之后就有一段时间不会再给，而再点一次按钮的读者应该拿到一条还能走的路。
  - **`beforeinstallprompt` 可能在 hydration 之前就发过了，而它不会补发。** 这里接受这个
    损失，没有为它在 `<head>` 里插一段抢跑的 inline script：漏掉它只少一个「一键」按钮，
    Chrome / Edge 的手动路径（地址栏那个图标、⋮ 菜单）是真的能走通的。为了给一个浏览器省
    一次点击，在每个页面的 head 里加一个 script，对一个以「打开就截图」为目的的站是笔亏账。
  - **装完就不显示了，而且是用 CSS 做的**（`[@media(display-mode:standalone)]:hidden`）。
    用 effect 探测的话，按钮会先渲染出来、hydrate 完再消失 —— 在报头这个位置闪一下再没了。
    CSS 查询覆盖不到的是**按下按钮的那个标签页**（它仍然是普通标签页），所以组件另外听了
    `appinstalled`。
  - **手机上只有图标，`sm:` 以上才出文字**，无障碍名字走 `aria-label`。这是算过的：报头那
    一行已经有域名 chip（这个字号加这个 tracking 大约 137px）和语言切换（90px），实测在
    323px 宽的视口里三个控件加两个 gap 只剩 4px 余量，把「存成 App」的文字放进去必然溢出。
    图标用的是 iOS 自己的 add-to-home-screen 字形（圆角方框加加号）而不是下载箭头 —— 后者
    承诺的是「有个文件要落进下载目录」，而这里要造的是一个图标。
  - **步骤文案在 `lib/install.ts`，不在 `i18n.ts`。** 这些字符串**就是那张分支表**：一个平台
    的名字、它菜单里的字样、选中它的判断条件，是一件事的三个部分，拆到两个文件里之后每次
    浏览器改菜单都要改两处。`i18n.ts` 只留按钮、标题、关闭这些外壳。
  - **菜单按钮一律先用文字说、再把字形放在括号里**（「点右上角的菜单按钮（三个点，⋮）」）。
    ⋮ 在 Manrope / 思源黑体里都有真字形（实测 5.75px 宽，不是 tofu），但 14px 下三个点很容易
    被读成两个 —— 写这段说明时的截图自己就读错了一次。
  - **Firefox 桌面版直接说「不支持」**，不给步骤。给一列最后指向一个并不存在的菜单项，比
    承认做不到更糟。
  - **平台判断全靠 UA 嗅探，而且这里没什么可辩解的**：要产出的是一句点名某个菜单项的话，
    而「点右上角的 ⋮ 菜单」不是任何 API 会报告的能力。代价是猜错只会印出错的步骤（不会报错），
    所以每个分支都退到「打开浏览器菜单，找……」的泛化说法，而不是自信地断言一件没把握的事。
    `guideKey()` 是纯函数（UA 和 `maxTouchPoints` 都是参数），19 个真实 UA 的判定跑过一遍：
    iPad 那条尤其要留着 —— iOS 13 起 iPad 发的是桌面 Mac UA，`maxTouchPoints > 1` 是唯一
    剩下的信号，判错就会给 iPad 递上 Safari 的「文件 → 添加到程序坞」，一个它没有的菜单。

**客户端组件现在是八个**：`DigestBody`（分类 `useState`）、`ShareButton`、`ShareSheet`、
`InstallApp`、`PullToRefresh`，加上根布局里三个不渲染任何东西的
`Analytics` / `ServiceWorker` / `ClickTracking`。**页面正文仍然全是服务端渲染的** —— 卡片、
摘要、报头、归档行没有一个跨过边界，埋点也是按「不把它们拖过去」设计的，见
[`TRACKING.md`](TRACKING.md)。（这句以前写的是「`DigestBody` 是唯一的客户端组件」，
分享面板落地之后就已经不准了。）

## 打分：五个维度各 1-10 分，总分由代码加总

**模型不再给总分。** 它给五个维度各一个 1~10 的整数加一句依据，代码求和（`lib/score.ts`
的 `SCORE_WEIGHTS` 和 `totalScore()`）。

| 维度 | 判什么 |
|---|---|
| `substance` | 删掉作者还剩什么（思想密度） |
| `surprise` | 颠覆直觉，还是老生常谈（值不值得复述） |
| `accessible` | 是否抛弃了行业黑话 —— **特别 geek 的给 1~2 分** |
| `relevance` | 能否触发智力共鸣（好奇心关联） |
| `quality` | 文章本身的做工（注水程度） |

**权重全是 1，满分 50，门槛 30 = 满分的 60%。** 维度一度是七个，见下面「维度合并」。

### 每个维度的档位必须无缺口

判据一度只写 10 / 8 / 5 / 1-3 四档（`relevance` 更少，只有 10 / 5 / 1-3），**9、7、6、4
全是空的**。模型在空档里只能自己猜，而它猜的方向一律往上 —— 这是分数挤在 7 的原因之一。

现在五个维度统一是 **9-10 / 7-8 / 5-6 / 3-4 / 1-2**，覆盖 1~10 无缺口。

**而且整体下移过一档。** 补全档位之后跑了一轮，七个维度里五个中位数还是 7，分数全挤在
43~55 —— 原因不是模型算错，是**档位描述本身写得太宽**。当时 `opinion` 的 7-8 档写的是
「立场清楚、有论证，但只靠一个例子」，那描述的就是一篇普通的好博客；而 5-6 档写「立场
看得见但主要在叙述」，听起来比大多数文章的实际水平差。模型是按字面对号入座的，落到 7 是
对的。校准段说「5 是默认」，档位文字说「典型好文章 = 7」，冲突时模型跟档位。

所以每个维度的描述整体往下挪了一档：原来 7-8 的文字挪到 5-6，7-8 换成「做了一件 5-6 档
覆盖不到的具体事，而且你得说出是什么」，9-10 保留各自的点名条件。**每个维度的 5-6 档都
明确写着「大多数文章在这里」**，其中三个直接点名了本日报的主体（普通好博客、tech 类文章、
历史/科学/别的行业）。

清单文的上限也从 7-8 挪到了 5-6：「**一份规则或建议清单外面包一层论点，上限就在这里**
—— 框架再好，读者带走的还是那份清单」（这条现在在 `substance` 里）。

**这条后来加了条件，因为它连实用文章一起压了。** 原文按「是不是清单」封顶，于是「写作的
唯一金科玉律：多读」这种文章无论有没有讲清道理，`substance` 都到不了 7；而 `surprise` 那
边它又正好撞在 1-2 档的例子上（`sleep is good for health`），`relevance` 就算给到 9 也只
有五分之一权重，拉不回来。现在改成**按有没有给出机制判断，不按体裁判断**：

- `substance` 7-8 增加一条 —— 读者能照做的规则，**只要文章说清了它为什么有效**就算这一档，
  而且要在 note 里把那个机制写出来，写不出就不是 7；5-6 的封顶改成「**理由单薄**的清单」，
  3-4 明确写成「只下断言、不给任何理由的 tips」
- `surprise` 5-6 增加一条 —— 结论老套不等于陈词滥调：**给出了机制或证据**的实用文章走 5-6，
  它的价值由 `substance` 和 `relevance` 去记；1-2 只留给「说了但没证」的断言
- `relevance` 9-10 明确写上「**做法也是行动**」—— 一种写作、训练、饮食、睡眠或工作的方式，
  只要具体到能照着做，和一个关于钱的决定同样是 9

**没有动权重**，这是刻意的：`SCORE_WEIGHTS` 上面记着「2/2/2/2/1/1 改成等权，排序和过线
文章一模一样」，能真正移动分数的是档位措辞，不是权重。

同时把最容易通胀的几档改成**可否证**的写法，要求 note 里点名具体东西，点不出来就不能给
高分（下面用的是合并后的维度名）：

- `substance` 9-10：**点名它能搬去解释的那个领域**，点不出就不是 9
- `surprise` 9-10：**说出读者原本相信的那个信念，并引出那句会被人原样复述的句子**，缺一样
  都不是 9
- `relevance` 9-10：**点名读者读完会改变的那个具体行动**，说不出就不是 9
- `relevance` 5-6：明确写着「**这份日报里大多数文章都该待在这里**，包括优秀的那些 ——
  有意思不等于切身」

最后那条是针对实测的：`relevance` 从可验证的判据（钱/健康/工作/住房）改成「能否触发智力
共鸣」之后，中位数从 4 顶到 7，单这一维就给每篇加了 3 分。历史、科学、别的行业本来就该
是 5~6，而那正是这份日报的主体。

权重曾经是 2/2/2/2/1/1，拿真实数据重算后发现**加权几乎不改变任何结果** —— 同一跑用等
权重算出来是同样的排序、同样 7 篇过线。一个不改变结果的旋钮只剩「必须保持一致」这一个
负担，所以去掉了。

**`score` 现在是 5~50，不是 0~100。** 这个改动之前的存档带的是旧量纲的分数，跨那个日期
不可比。

**为什么模型不许自己给总分。** 问它要一个 0~100 的数，2026-08-20 那一跑 19 篇文章只回了
**6 个不同的值**（85 五次、82 六次、78 四次、72 三次、62 一次）—— 这个字段实际只有六档
分辨率，因为模型会从一小把整数里挑。拆成六个小判断，它必须真的做区分，区间由算术产生。

`accessible` 是这次改动存在的理由：一篇深度 geek 的调查以前能靠「确实是论证 + 机制可
迁移」拿到 85 分，规则里没有任何地方能把它折价。现在它是六分之一，而且 prompt 里写明
「**再出色也要给低分** —— 出色应该体现在 `substance` 上，不是这里」。

**天花板机制没有了。** 原来测试 ①②③ 是硬顶，产品发布无论写得多好都封在 20 分档；求和
没有顶，一篇写得漂亮的公告可以靠别的维度往上爬。如果这被证明不够，**顶应该加在代码里
（`SCORE_WEIGHTS` 旁边），不是加在 prompt 里**。

### 维度合并：七个在量三件事

拿 22 篇的实测算了相关性，七个维度实际只在量三件事：

```
opinion ↔ judgment    0.88      judgment ↔ transfer  0.76
novelty ↔ hook        0.76      opinion  ↔ transfer  0.73
accessible 跟所有维度  0.17~0.42   ← 唯一真正独立的
```

所以「权重全是 1」名义公平、实际是 **3 : 2 : 1 : 1** —— 一篇文章的排名主要由「它有没有
自己的思想」这一个判断决定，只不过被问了三遍。这也解释了为什么当初调权重毫无效果。

更刺眼的是：**去掉任何单个维度，排序相关都在 0.964~0.999**，没有一个是不可替代的。而按簇
合并成四维，排序相关 **0.962** —— 跟去掉单个 `novelty` 的影响一样大，也就是说多出来的三维
不产生任何排序信息。

合并后是五维：`substance`（原 opinion + judgment + transfer）、`surprise`（原 novelty +
hook）、`accessible`、`relevance`、`quality`。满分 50，门槛 30。

**合并的收益不是分数更准（排序几乎一样），是改判据时它只动它自己。** 以前改 `opinion` 的
档位实际上是在动 3/7 的权重，那就是为什么每次调整的效果都难以预测。

合并后那一跑的结果是最好的一次：五个维度里四个均值落在 5.0~5.9（上一跑七个里五个中位是
7），过线 9/18 = 50%，`surprise ↔ relevance` 相关 -0.01（完全独立），去掉单维对排序的影响
从 0.964~0.999 变成 0.909~0.994 —— 每个维度终于都在贡献信息。

**`quality` 是唯一还有问题的一个**：它跟 `substance` 相关 0.73，去掉它排序只变 0.994。
判据里原本写着「the structure IS the argument」这类跟 `substance` 重叠的表述，模型就把
「做工好」和「有思想」当成一件事了。现在它的判据改成**纯机械**的 —— 只数注水、重复、
该有证据处的空缺，并且明确写了「不要考虑这篇有没有洞察、题材有没有意思、写给谁看」，附带
一条自查：**如果你给 `quality` 写的理由也能当 `substance` 的理由，那你没在判做工。**

### 星星按门槛起算，不是按满分

`lib/score.ts` 的 `starCount()`，页面和分享海报共用一份（以前各有一份实现，会各自漂移）。

```
30–33 → 1 星    34–37 → 2 星    38–41 → 3 星    42–45 → 4 星    46–50 → 5 星
```

按满分均分五等分是错的：实测一跑分数落在 36~45（当时满分 80），`score / 20` 让**每一篇
都是 2 星**，5 星在构造上就到不了。所以带宽取「门槛到满分」的 20 分，每 4 分一颗。

两个边界：**一星是门槛，不是零** —— `alwaysPublish` 的源跳过门槛，已发布的文章可能低于
30，那是真实的一星；只有 0 分（打分那轮没答上）才返回 0、页面什么都不画。旧存档带的是
0~100 的分数，会全部显示五星，不做转换 —— 那些数字本来就不可比。

**它仍然铺不开，而那是分数的性质不是这套算术的问题。** 实测过线区间只有 6~7 分宽
（30~36），五档怎么切都不合理：4 分一颗全挤在 1~2 星，2 分一颗则 1 分之差就跨档。这一条
记在这里而不是修掉，因为要修的不在这个函数里。

### 启动时校验 prompt 和权重表的键名

`SCORE_SYSTEM` 里的五个维度是手写的（每个都带自己的判据，只能手写），所以在 prompt 里
改了名而忘了改 `SCORE_WEIGHTS`，`readReview()` 就会去找一个任何回复里都不存在的键 ——
**每篇文章都判不出分、都记 0、都掉到门槛以下，跑出一份空日报，而且不报任何错。**
`argument` 改名成 `novelty` 那次就是这样。

现在模块加载时会逐个检查权重表里的键在 `SCORE_SYSTEM` 里出现过，对不上直接抛异常。

### `SCORE_EXAMPLE` 的分数也是规格

它一度示范的是 9/9/8/9/9/8，而上面的校准段写着「5 是默认、8 少见」。**模型跟的是示例**
—— 连续两跑都没有任何维度超过 8，多数维度不超过 7，上半段挤成 5 分宽的一条。

现在示例故意是一篇**好但不出彩**的文章：`novelty 7 / hook 7 / accessible 8 /
transfer 4 / judgment 6 / relevance 9`，总分 41。一个 9 分写清了凭什么，一个 4 分理直
气壮地待在旁边，全场没有 10。

**五个维度缺一个就算未判定**，不是那一维记 0 分 —— 部分回复正是旧的单 `score` 字段藏住
的失败模式，少一个数看起来跟给了个低分一模一样。越界的分数（11、0）会被夹到 1~10 而不是
丢掉整篇：那是模型在一个它其实理解的标尺上冲过了头。

### 第一跑的结果，以及为此加的校准

分辨率问题解决了：**不同分数取值从 6/19 涨到 22/30**，范围 24~76。geek 惩罚也生效 ——
Rust 恶意包 `accessible 2` → 52 挡掉，Show HN 的 125M 模型 `accessible 3` → 57 挡掉，
AliExpress 的 WebAudio 调查 `accessible 5` → 69 勉强过线。

**但上半段挤成一团**：过线的 15 篇全落在 63~76，满分 100 完全没用到。分维度看原因很清楚
—— 过线篇的 `argument` **全是 7 或 8**（零区分力），`transfer` 全场没有一个超过 7。

光在 prompt 里写「用满 1-10 区间」没有效果。有效的是**给出期望分布**，现在写的是：

- **5 是默认值** —— 一篇写得不错的普通文章，多数维度就该是 5
- 30 篇里的形状：多数落在 4~6，**7 分必须能说出具体理由**，8 分少见，9~10 可能一天都不出现
- 「要写 7 之前，先问一句什么情况才算 9；答不出来，那就是 5 或 6」
- **低分是常态**，2 和 3 是给真实缺陷的真实分数，不是羞辱

每个维度还补了 8 分和 6~7 分的锚点，因为原来只有 10 / 5 / 1-3 三档，中间那段全靠模型猜。

**`judgment` 加了一条针对清单文的规则**：第一跑里那篇 21 条礼仪清单 `judgment` 拿了 8 分
（理由不算错 —— 清单外面确实包着论点），过线后正文被逐条译成 1265 字。现在写的是「编号
清单外面包一层论点，最多 8 分，清单比论点长得越多掉得越快」。

**门槛还是 60，没动。** 加了校准之后分数会整体下移，跑一轮看新分布再定 —— 现在改就是拿
一个猜的数换另一个猜的数。

下面几节是**上一版五步规则**的记录，那套规则已经不在 prompt 里了，但它踩过的坑（尤其
「可迁移性不是圈内精彩程度」和两条反向豁免）在写维度说明时全都用上了。

## 上一版：观点优先，不是新闻聚合（历史）

这是一份**读观点和分析**的日报，不是用来追新闻的。

prompt 里是显式的五步，开头就写清了各条之间怎么作用：**1~3 是天花板**，踩中就压到
那个档，踩中几条取**最低**的那个；**4 是加分**，只在天花板允许的档位内移动，
**不能把文章抬过天花板**；5 是最终落点。条目化本身是有效的 —— 同一批文章改成
一条一条之后，天花板咬得更紧，分数区间从 12~72 拉开到 4~70。

第一个问题是**「论证还是通告」**：这篇文章有没有推导出一个读者可以反对的主张，
还是只在报道某件事发生了？

判据写得很直白：**如果整篇能被复述成「X 发生了」而不损失什么，它就是新闻**，
压到 30 分档以下，把位置让给有论点的。发布会、跑分表、版本号、链接汇总贴都属此列，
无论那件事本身多重要。

第二个问题是**「圈外人能带走什么」**。读者博览但不是这一行的从业者，也不打算成为。
所以单个库的内部实现、单块芯片的某道工序、某个浏览器的解码怪癖、某个框架的
release notes —— 写给已经在圈里的人看的东西 —— 一律压到 20 分档，**除非它揭示的机制
能迁移出去**。判据是可迁移性，不是圈内的精彩程度：

- `Tailscale 追到 SQLite 里 16 年没被发现的 WAL reset bug` → 78 分。它讲的是静默数据
  损坏怎么藏住自己，这件事在任何系统里都成立。
- `Spaghettifying DRAM`（DRAM 电容怎么刻蚀）→ 不迁移，20 分档。

这一条是为 HN 加的，但它对所有源生效。

第三个问题是**「给的是判断，还是一份清单」**。作者提供的是筛选还是判断？本周最佳读者
评论、「我最近读的书」、转述别家报道的一段 —— 读者带走的是「有这么些东西」，那不叫
带走。这类压到 20~30 分档，无论它指向的材料多好。判据：**把作者删掉，看丢了什么。**

两条反向豁免，都是实测撞出来的：

- **评别人的书或论文不算转述**，只要它有论证。「音乐版权的规则不是天然如此，是一层层
  临时补丁堆出来的」是可以反驳的判断，按论证算分；「这本书讲了 A、B、C，值得一读」
  才是穿着书评外衣的清单。
- **篇幅不是判据**，短文照样可以有论证。「外置卷帘在美国买不到，因为木框架房子装不了，
  也就没有供应链」四段话，有主张也有机制，胜过一篇长而工整的二手转述。

加这一条之前，`Funniest/Most Insightful Comments Of The Week`（纯评论汇总）拿了 55 分
并且上了页面，同一天一篇有论证的书评只有 42。

第四个问题是**「普通人爱不爱看」** —— 唯一一条**加分**项，最多 +15。前三条决定这篇
文章能待在哪个档，这一条决定它在档内的位置。**它不能把文章抬过天花板**：一篇写得
很好看的产品发布，仍然是产品发布，仍然压在 20 分档。这是有意的选择，改成可以突破的话
日报就会开始收发布会新闻。

得分项写成了可操作的四条：

- 跟人实际过的日子有关 —— 钱、健康、工作、房子、上学、城市、AI 正在对饭碗做什么
- 里面有人、有场景，不只有命题 —— 某人在某地做了某事，结果是这样
- 有钩子 —— 一个和你预设相反的事实、一个本身就惊人的数字、一件你会在饭桌上讲起的事
- 不需要背景就能进入，不用先解释什么它才开始有意思

两条**不得分**：只有圈内人觉得精彩（那是第二条，它是压不是加）；正确、扎实、
但从第一行到最后一行都在讲抽象。最后压一句**「诚实点，别慷慨：多数文章 +0~+5，
+15 留给读者会转发给朋友的那一篇」** —— 不写这句，加分项会变成普涨。

实测它在按设计工作：`我们追踪了一箱珍本书，终点是亚马逊的 AI 训练设施` 42 → 62
（有人、有场景、有追踪器），`Trump 的反华保护主义延伸到数据中心` 55 → 68（钱和饭碗），
`独立创始人用 Codex 做时尚品牌` 22 → 34（涨了 12 分但仍在门槛下，天花板没被突破）。

### 分数有 ±20 的方差，单次运行不能当结论

同一份 prompt、同一篇文章连跑三次：

```
52  72  62   Things you cannot buy in America?
62  58  65   音乐版权书评
17  18  25   Techdirt 本周评论汇总
```

有观点的两篇均值在 62 上下但单次能飘到 52，纯汇总那篇稳定压在 17~25。**所以某篇文章
在某一天掉出门槛是正常方差，不是规则出了问题** —— 上面那次 18 篇的对比里，
`Things you cannot buy in America?` 就有一次打出 35 掉出了门槛，连跑三次才确认是尾部。

改打分规则时要 n≥2 稳定复现才算数，这和 `### 改 prompt 之前先读这一节` 里的结论一致。

### `publishMinScore`：唯一一道门槛

`publishMinScore`（现在是 **30**，满分 50 的 60%）决定一篇文章进不进页面。低于它的
**不写进页面，但写进 JSON 的 `rejected` 数组** —— 标题、链接、源、分数，按分数从高到低排。

> 本节后面提到的 35 / 40 都是**旧量纲（0~100）**上的数字，那时候分数是模型自己给的。
> 换成五维求和之后量纲变成 5~50，两者不可比。

`rejected` 特意不复用 `folded`：后者在页面上是「其他动态」那一栏，会显示出来。留这份
记录是为了事后能查 —— 「那篇怎么没进来」有答案，评分规则哪天开始误伤好文章，在文件里
会比在页面上先看出来。没有任何组件读它。

**曾经有两道**，是个阶梯：`publishMinScore` 决定进不进页面，`minScore` 决定上不上
卡片，夹在中间的降级成一行。改成「全部出卡片」之后，「值不值得一张卡片」和
「值不值得发布」变成了同一个问题，于是两道并成一道，取值沿用旧卡片门槛的 40 而不是
旧发布门槛的 35 —— **本来不配拿卡片的，不该因为改版就默认得到一张。**
`minScore` 和 `categories[].cardCount` 都已删除。

它补的洞是：「什么都不丢」意味着打分器判对了也没用。`Grok 4.6`(25)、
`Qwen3.8-2.4T`(20)、`Codex in ChatGPT desktop app for Linux is now in preview`(22)
全部被正确地判成了低分，然后全部照常出现在页面上。**版面缺的不是判断力，是一个安放
「判对了、但不值得看」的地方。** 实测（门槛 40）：8-12 由 24 篇降到 16 篇，
8-13 由 17 降到 10。

它加在 job 里而不是组件里，所以归档的旧 digest 不会被一条它写入时还不存在的门槛
重新过滤 —— 打开 2026-08-13 那期，仍能看到当时那三条 20~35 分的发布公告。

门槛**只对模型真正判过分的文章生效**。模型调用整体失败时所有分数都是 0，只看分数会
把整页清空 —— 那是把「降级」变成「空白」，而这个 job 的整个设计就是为了避免这件事。
所以未判定的文章照常占位并以纯标题渲染，和门槛不存在时一样。

判据是 `Verdict.judged`，**不是「有没有摘要」**。打分独立成第一轮之后，「没有摘要」
有了两种含义：被门槛刷掉（本来就不该写摘要）和调用失败（该保留）。拿有没有摘要来判，
会把所有 40 分以下的文章全部以裸标题的形式放回页面 —— 正好和门槛的意图相反。

## 摄入上限 `maxPerRun`

`sources[].maxPerRun` 限制一个源在**一次运行里最多进来几篇**。目前两个源设了：
Hacker News 5（原为 10）、XDA · AI Tools 3（原本不限），理由都在上面订阅源那节。
其余不限 —— 新加的 11 个源频率最高的 Conversable Economist 也只有 0.57 篇/天，
不需要上限。

它加在**抓正文之前** —— 时间窗口过滤之后、并发抓取和送模型之前。这是关键：
这个上限的意义就是「不为这些文章花钱」，而钱花在抓第三方页面和摘要的 input token 上，
放在后面截断等于白截。按发布时间取最新的 N 篇（打分之前没有别的排序依据）。

**别和已删除的 `maxPerDay` 混淆。** 那个是版面配额（一个源能占几张卡），已经删了；
这个是摄入上限（花不花钱）。

实测数据（27 篇的一天）：

```
Hacker News          13 篇  112,195 字符  53%   ← 它一个源占一半
Not Boring            1 篇   20,000 字符   9%
其余 7 个源           13 篇   80,883 字符  38%
```

HN 占大头是因为它指向任意第三方站点，每篇都按 `BODY_CHAR_LIMIT` 上限抓。

**但限制篇数省不了多少**，因为主因是长度不是数量：

```
限制前                85,231 input tokens   全年 $5.40
HN 限 10 篇            81,839                全年 $5.11
```

真正的杠杆是给 HN 单独降 `BODY_CHAR_LIMIT`，但那是拿摘要质量换每年 0.5 美元 ——
一篇 2 万字的长文只看前 8000 字，判断会失真，而把这个值从 6000 提到 20000
正是为了修那个问题。**所以不给单个源降预算，要省就限篇数**（HN 5、XDA 3）。

## 正文预算 `BODY_CHAR_LIMIT`：为什么是 80000

20000 截掉的比看起来多得多。把上限临时撤掉、量 14 天窗口内的 136 篇：

```
notboring              1/3 篇超限   中位  9,180   最长 84,933
noahpinion             3/8 篇超限   中位 18,368   最长 80,993
acx                    2/10 篇超限  中位 11,642   最长 68,463
danluu                 1/1 篇超限   中位 63,384   最长 63,384
neciudan               1/2 篇超限   中位 47,898   最长 47,898
platformer             2/5 篇超限   中位 14,745   最长 36,184
damodaran              1/1 篇超限   中位 32,646   最长 32,646
worksinprogress        2/3 篇超限   中位 24,590   最长 28,187
craigmod               2/3 篇超限   中位 23,558   最长 27,249
lennys                 1/11 篇超限  中位  2,995   最长 26,279
construction-physics   1/4 篇超限   中位 18,585   最长 25,445
```

**17/136 篇（12.5%）被截，横跨 11 个源** —— 不是只有那两个显眼的长文博客。Not Boring
和 Noahpinion 的中位数都在限内，所以从平均值上看不出问题，但它们各自最长的那几篇正好
是最值得读的深度文。

为什么是 80000 而不是更多：**曲线在这里就平了。**

```
cap  20000    74,699 字符/天   ≈ 31,737 input tokens/天   （基准）
cap  40000    88,863                 37,755                +19%
cap  60000    95,141                 40,423                +27%
cap  80000    98,845                 41,996                +32%
cap 120000    99,268                 42,176                +33%   ← 只多 0.4%
```

样本里最长一篇 84,933 字符，所以 80000 已经覆盖 99.6% 的正文，再往上买不到东西。

为什么不更少：`BATCH_SIZE` 是 1，**一次请求只带一篇正文**，所以最长那篇也只有约 36k
token，对着以十万计的上下文远不到边。批量大小是 1 的这个决定（见摘要那节，为了 JSON
可靠性）顺带让正文预算可以给得很松。

成本 +32% 听起来比实际严重：它涨的那个基准本身已经因为 HN 限 5、XDA 限 3 而**腰斩**过，
所以落点约 $2.7/年，仍低于两项改动之前的 $5.40。

## 正文是一个字符串，不是段落数组

每篇产出 **一句话论点（`thesis`）+ 正文（`text`）**。`text` 是**一整个字符串**，
里面的**空行就是分段**，除此之外没有任何标记语言。渲染端统一走
`lib/paragraphs.ts` 的 `paragraphsOf()`，页面和分享海报（连海报的高度算术）读的是
同一个拆法。总字数按文章本身的长短算（见下面「长度按文章长短算」），标准是
**读完不用再打开原文**。

**字段的形状决定了文字的形状**，这条被两代结构验证过：

- `points: string[]` —— 模型把每条压成孤立短句，卡片读起来像电报，六条断言彼此
  没有承接。
- `paragraphs: string[]` —— 修好了电报感，但换来同一个毛病的温和版本：数组先问
  「几段？」再问「要说什么」，于是模型是在填格子数，断句落在配额用完的地方，
  而不是论证转弯的地方。同时代码里还配了段数区间和每段 90 字的硬上限
  （`summaryParaMaxChars`），三条规则互相矛盾。
- 现在的 `text: string` —— 只要求散文，段落在哪儿断成了写作内部的决定。**段数**的
  算术（那个 `分 N~M 段` 的区间）彻底删掉了，不会再回来。

**每段 90 字的上限（`summaryParaMaxChars`）删过两次，现在第三次装回来了**，而且大概不会
再删。三次删除之后的实测，每次最长段都更长一点：

| 当时的约束 | 最长段 | 那一篇 |
|---|---|---|
| 只有「排版极简」 | 251 字 | —— |
| 加了「最多三个要点」 | 319 字 | —— |
| 加了「小标题最多 3 个」 | **424 字** | 21 条清单文，1757 字 / 预算 590 = **2.98×** |

规律很清楚：**堵一个洞，水就从另一个洞出来。** 限制要点数，它把内容塞进小标题；限制小标题
数，它把内容塞进段落 —— 最后那篇把 21 条规则归并成 4 个主题（这正是我们要求的），然后每个
主题底下写一大坨。**字数必须限制在文字实际所在的地方。**

段数仍然完全由模型定。段数的算术（`分 N~M 段` 区间）是永久删除：数字区间是一条目标，模型
会照着凑；而上限不是目标，没人奖励你写满，并且**看一段就能自查** —— 这是实测中唯一守得住
的那类规则（第三人称守住 19/20，软性字数预算守住 3/20）。

**子标题是可选的，而且是模型自己声明的。** 正文里唯一允许的 markdown 是 `## `：
以它开头、自己占一块的段落被认成小节标题（`blocksOf()`），标记被剥掉，页面上加粗、
并且贴紧它引出的那段正文，海报上同样加粗。1~6 级都认，井号后面的空格可有可无
（中文里常写成 `##标题`）。**除此之外一概不解析** —— 没有 `**加粗**`、列表、链接、
引用块，写了就在屏幕上露出字面符号。

这一版换掉了一个启发式判定。原来靠「开头是不是 `1.`」来猜，因为纯文本里数字是唯一的
标记 —— 2026-08-20 那一跑，一篇被翻译过来的清单文（21 条礼仪）被判成 **21 个连续
子标题，全部加粗**。那些块长 49–144 字，而这份日报里真正的子标题是 12–17 字，所以
长度门槛也能分开它们，但那只是换一种猜法。`## ` 是声明，猜的成分归零：以数字开头的
段落现在就只是以数字开头的段落。

字号和行高**故意跟正文一样，只有字重不同** —— 海报高度是数
`layoutParagraph()` 的实际行数算出来的，而字宽测量不看字重，所以加粗不会让图片和
它声明的高度打架，放大字号就会。子标题上方的间距比段间距大 4px，这一条
`posterHeight()` 里是逐块累加的，不是拿段数乘常量。

prompt 里**加与不加都是对的写法**，由文章形状决定：几个点各自站得住、连着读会让人找
不着自己在哪儿的，分节（通常 3~4 节）；一条线推到底、链接汇总、两三百字的短文，不分。
两边都不硬来 —— 硬凑的「1. 2. 3.」比不分节更难读，一屏没有落点的长正文也一样累人。

`SUMMARY_EXAMPLE` 里不带子标题，这是**折中而不是偏好**：一个示例没法同时示范两种形状，
而它示范的那种会被当成缺省。选不分节的那种，是因为它是更安全的过量方向 —— 本该分节
却没分，只是密一点；不该分却分了，会出现一个小标题底下只有一句话。平衡靠 prompt 里
两种情形都写清来保证，渲染端不受影响，出现子标题就照样加粗。

## 摘要 prompt：2026-08-21 整段换掉了

`SUMMARY_SYSTEM` 现在很短。风格部分只有一段角色设定加五条指南，原文照抄，不再有
分节讲解：

```
请你充当一位擅长“通俗讲知识”的高中历史/社科老师。抓住文章的重点内容和观点，
改写成极简、有趣、易懂的风格，让高中生也能轻松理解

写作风格指南：
- 拒绝照本宣科：严禁使用晦涩的学术名词和长难句，多用短句和口语化表达
- 巧用现代类比：适当引入现代生活中的概念或流行语（如：KPI、拼团、C位、打卡、运营等）
- 场景化/故事化：把宏大的历史概念转化为普通人的“生活视角”
- 排版极简：多用小标题、序号，结尾附带一句“一句话总结/金句”
- 生动幽默：语气热情接地气，像在和朋友面对面聊天，而不是在讲台上念课本
```

剩下的都是机械契约，删了流水线就断：字段清单、一篇一条按 `index` 对应、不许用直双引号、
不许塞真换行、`## ` 是正文里唯一允许的 markdown、分类只能从给定列表选、标题只译不改写。

**同时删掉的规则**（下面几节还在描述它们，那些是历史）：

| 删掉的 | 原来是什么 |
|---|---|
| 每段 90 字上限 | `summaryParaMaxChars`，连 config 键一起删了 |
| 第三人称、不许出现「我」 | 曾经是这份 prompt 里唯一守住 19/20 的硬规则 |
| 一句一条逻辑线 + 正反例 | 三节散文，含 Town CEO 那个反例 |
| 收尾段的写法规定 | 现在只剩指南里那句「结尾附带一句金句」 |
| 子标题什么时候该用 | 现在只剩指南里那句「多用小标题」 |
| ~~英文那一整半~~ | **已装回来**，见下面「英文那一半」 |

**这是一次有意的取舍。** 被删掉的那些规则不是没用 —— 2026-08-20 那一跑量过：明确、
单一动作、可自查的规则（第三人称）守住 19/20，而软性的字数预算只守住 3/20，45% 的段落
超过 90 字、最长 251。删掉硬约束之后，撑住节奏的只剩「排版极简」这五个字。**如果 251 字
的墙回来了，上面那张表就是可以往回装的东西。**

### 概要是第三人称（第二次装回来）

正文里不出现「我」「我们」「咱们」「笔者」。这条规则第一次存在时实测守住 19/20，随
2026-08-21 那次 prompt 整段替换一起删掉，删掉之后一跑就有 **7/12 篇出现第一人称**。

它不是文风偏好，因为坏掉的方式有两种，而第一种是真的错：

```
概要在假扮原作者   「最近我遇到个怪事：我的蓝牙耳机支持多点连接」
                  「直到我包装了 AudioContext，才发现页面悄悄创建…」
概要跟读者称兄道弟  「我们总觉得，只要把问题说得足够严重，大家就会行动起来」
```

第一种里的「我」是**原文作者**，而正文里没有任何线索能让读者判断这一点 —— 读起来就像
概要作者自己遇到的事。要交代是谁在说就点名：「作者发现」「这位工程师发现」。

**「你」不受影响** —— 设问和把读者拉进场景照常用，那个「你」指任何人。

顺带修了一个自相矛盾：`SUMMARY_EXAMPLE` 里那句「**我们**把时间拨回 4000 年前的古中东」
本身就违反这条规则。示例就是规格，规则和示例打架的时候模型跟示例 —— 去掉那两个字就够了，
句子读起来一样。

### 补回来的两条硬规则：三个要点 / 小标题最多 3 个

换完 prompt 那一跑，超预算 14/15、中位 **1.42×**（上一版 1.30×），最长一块 319 字。
最差的是那篇 21 条礼仪清单：**1265 字 / 预算 590 = 2.14×**，逐条译了。

所以加了一条**可数、可自查**的约束 —— 这正是这个模型守得住的那一类规则：

> **一篇最多讲三个要点，所以小标题也最多 3 个 —— 这是同一条规则的两种说法。**
> 写完数一遍井号，超过三个就是错的：合并、或者砍掉一整节，不要靠缩短每节来凑。

「最多三个要点」单独放出去时守不住：《新礼仪基础》那篇 21 条清单，一跑写 320 字（守住了），
下一跑写 1253 字、**12 个小标题**（完全无视）。「要点」是抽象概念，模型没法自查；**井号
可以数**。所以现在两种说法都写进 prompt，互为对照。

**示例也跟着砍到 590 字、3 个小标题。** 上一版示例是 741 字、4 个小标题 —— 超过 650 的
上限，也超过它自己要求的三个要点。示例就是规格，那一跑的 1.42× 就是它拉出来的。砍掉的是
「每天都是生存闯关游戏」整节：它是四节里最像逐条清单的一节，留在示例里会跟「绝不逐条
翻译」这条自相矛盾。文字一个字没改，只是少了一节并重新编号。

### 长度按文章长短算，不是固定额度

原本是一刀切的 120~450 字。拿 14 天 63 篇量了一遍，**额度和文章长短完全脱钩**：
1 分钟的链接贴中位数 254 字，65 分钟的长文 279 字。短文被撑到额度，长文被压进额度，
而**压缩正是摘要变得不可读的原因** —— 三件不相干的事塞进五个 80 字的段落，那是电报。

现在 `budgetFor()` 用 `readingMinutes` 算（`reading.ts` 已经把 CJK 400 字/分和英文
230 词/分归一了，中文源和英文源不会因为字符密度不同而被区别对待）。它返回**一个数字**，
就是中文正文的字数上限，没有段数：

```
上限 = min(summaryMaxChars, round(110 + 200 × ln(阅读分钟 + 1)))
```

取对数而不是成正比，因为**压缩比应该随长度上升**：1 分钟的链接贴只有一件事要说，
250 字已经宽裕；60 分钟的长文有十几件，也不可能给它 12000 字。

| 阅读时长 | 额度 |
|---|---|
| 1 分钟 | 249 |
| 5 分钟（中位数） | 468 |
| 10 分钟 | 590 |
| 14 分钟起 | 650（撞天花板）|

曲线原本是 `90 + 160 × ln`，随「高中老师讲知识」那版风格一起抬了约 24%（中位数
377 → 468）—— 类比、场景、设问都是要花字数的，那是它们该花的。`summaryMaxChars`
（现为 650）只是曲线的天花板，14 分钟以上的长文才够得到；曲线的**次序**没变，短文
拿到的空间仍然远少于长文，那本来就是设这条曲线的理由。

**`summaryMinChars` 已经不再告诉模型任何事**，只留给 `report()` 统计「有没有短过头」。
写死的字数下限本身就是一条凑字数指令，和「覆盖全文」凑在一起，模型唯一能同时满足
两者的动作就是压缩。

### 额度是口头约束，而且它经常被突破

**没有校验、没有截断、没有重试。** 额度写进请求，模型守不守是它的事，`report()` 事后
数一遍，仅此而已。这是有意的选择：截断会砍掉收尾段（每篇必须有的那段「所以呢」）或者
断在半句上，而校验加重试要为一次超 20 字重发整个请求。

**实测的破限率**（10 篇过了门槛的文章，中英合并成一轮之后）：

| | |
|---|---|
| 超出各自额度 | 8/10，最多超 244 字（额度 423，写了 667）|
| 有段落突破每段 90 字 | 6/10，最长 122 字 |

> 这组数字量的是**还有段数区间和每段 90 字硬上限**的那个版本。两条规则现在都拿掉了，
> 段落长度不再有可破的限，所以第二行只作为历史记录留着。

固定 450 的年代是 13% 的篇目超标、15% 的段落超 90 字。**中英合并到一轮之后，长度纪律
明显变差了** —— 这是那次合并的代价，和它换来的（少一轮调用、两半不会漂移）一起记在
这里。单独跑中文那一轮时超额比例低得多。

试过一次没用的修法：把 budget 那行从「这篇最多 N 字」改成「中文正文最多 N 字（英文不
计入）」，猜测是两种语言让额度归属变得含糊。超额比例从 9/10 变成 8/10，等于没动。

所以**动态额度解决的不是「守不守得住」，是「该给多少」** —— 长文不再被压成电报，短文
不再被撑到额度。破限这件事它没有解决，也没打算解决。

### 但「段落」修完之后，冒出了相反的毛病

改成段落 + 「不能丢数字和案例」之后，模型走到了另一个极端：**一段就是一个长句**。

```
段1 (92字)：Town CEO 认为 AI 代理将取代传统软件，但当前仅能消除知识工作者 10-20%
的琐事，主要因为大多数人不了解 AI 能力，且习惯改变缓慢，如同 iPhone 普及耗时十年。
```

92 个字、5 个分句、0 个句号。同期还有「82%的工程师」「1.6万行Go工具」这种中英粘连，
`CYP1A2`／`paraxanthine` 一类术语裸奔，通篇「主要因为」「且」「综合权衡」「而非」。
读起来是论文摘要，不是中文。

**病灶在 prompt 自己的示例里 —— 它在主动教这个腔调：**

- `"3-5 sentences that connect — 具体来说, 原因是, 但, 结果是"`，「具体来说」正是最典型
  的书面语连接词
- 正例写成 `"OPT 扩展使本土高技能就业增长 0.5%、工资增长 1%，说明高技能移民并未挤出
  本地人"`，「使…增长」「说明…并未挤出」名词化加无主语，正是不地道的来源
- `KEEP THE SPECIFICS` 配 `"五步链式每步 95% 成功率，整体只剩 77%"`，教它把信息压到极限

**还有一个结构性原因：每段上限原本是 `ZH_MAX / 2.5`。** 300 字除成三段就是 120 字一段，
而模型会把这 120 字填满 —— 用一句话填满。所以现在两个数**反向移动**：总长 300→420，
每段 120→90。段落上限干的是文风指令干不了的活：**90 字装不进五个分句**，它只能断句。

### 现在的文风规则

prompt 里用中文直接写（用英文描述中文文风是隔了一层）：

- 一句一个意思，每句不超过 35 字，并把上面那个 92 字长句作为反例、拆好的版本作为正例
- 口语连接词（但是／不过／因为／所以／问题在于），明确禁用「综合权衡」「而非」
  「其中」「且」「基于」「使得」。**「具体来说」「值得注意的是」后来从禁用表里拿掉了**
  —— 它们是换话题时的路标词，禁掉之后每段都是冷启动，段落之间接不上
- 多用动词少堆名词：「命中缓存一次只要 2 分钱，是没命中的五十分之一」，而不是「缓存
  命中的输入价格为未命中价格的五十分之一」
- 中文与英文、数字之间**加空格**：「Token 的输入价格」「1.6 万行 Go 代码」
- 术语第一次出现就地解释：「paraxanthine（咖啡因在体内的代谢产物）」
- 允许设问再回答，允许「你」和「我们」
- **可读性优先于覆盖面**：字数紧就砍掉一个点，绝不把两个点压进一个长句

示例（现在叫 `SUMMARY_EXAMPLE`）也跟着重写了，因为在 JSON mode 里**示例就是规范** ——
光改指令、留着旧腔调的示例，模型跟示例走。

### 「示例就是规范」这一条踩了两次

同一个坑连着掉进去两回，都是**指令和示例打架，模型跟示例走**。

第一次：只说「短句」和「宁可少讲一个点」，模型把它读成了「少写」，62 分的文章只给
150 字。补了一句**短句不等于少写**，明说有料的该写到 300 字以上。

（**这条后来被删掉了。** 它和「LENGTH IS A HARD CEILING」「真正要砍的是长句，不是
内容」凑成了一组互相打架的规则 —— 下限 300、上限 450、又不许丢内容，模型唯一能同时
满足三条的动作就是把每件事压成一句。一份三主题的周刊因此写成了 346 字的电报。删掉
下限和「不许丢内容」之后，「可读性优先于覆盖面」成了唯一的取舍规则。）

第二次：把总长从 420 提到 600、段落数从 3~5 改成 4~7，结果**总字数反而降了**（308 →
228）。因为示例的段落只有 20~30 字，六段加起来才 180 —— 它和「400 字以上」
那句指令直接矛盾，模型照抄了示例的段落长度。同期还有一句「一句话独占一段完全可以」
在帮着鼓励空段落。

修法是把示例的段落写到真实目标长度（每段 2~3 句、60~85 字），并把那句改成
「段落要短，但不要空……七个 25 字的段落加起来才 180 字，那是把内容砍掉了，不是把它
排开了」。

三轮实测（同一批文章）：

```
最初    313 字 / 3 段   单句最长 92 字   ← 一段就是一个长句
第二轮  308 字 / 4 段   单句最长 49 字   ← 句子拆开了
第三轮  500 字 / 7 段   单句最长 58 字   ← 段落也饱满了，每段 50~88 字
```

同一批里的链接汇总贴是 165 字 / 5 段 —— 额度是上限不是指标，没料的文章仍然短，这是对的。

### 句长上限是错的，换成「一句一条逻辑线」

最初的规则是「每句不超过 35 字」。把阮一峰那篇缓存文章拿来量，才发现**这条比要模仿的
对象还严**：

```
阮一峰 30 句：平均 34.2 字，中位 34，最短 9，最长 71
  超过 35 字的：12/30 = 40%
  超过 50 字的： 4/30 = 13%
```

35 字差不多是他的**平均值**，不是上限 —— 他 40% 的句子都会破这条线。

**病因不是长。** 对比一下他最长的那句（71 字）和最初那个坏句子（92 字）：

```
好（71 字，一条因果链）
  如果对话的间隔特别久，下一次输入跟上一次之间超过了 10 分钟，缓存就被删除了，
  模型收到上一轮的提示词，就不得不重新计算，收取的费用就变成了 1 元。

坏（92 字，四种逻辑关系）
  Town CEO 认为 AI 代理将取代传统软件，【但】当前仅能消除知识工作者 10-20% 的琐事，
  【主要因为】大多数人不了解 AI 能力，【且】习惯改变缓慢，【如同】iPhone 普及耗时十年。
```

好的那句更长，却读一遍就懂：条件 → 缓存删除 → 重新计算 → 价格变 1 元，从头到尾**方向
不变**。坏的那句把转折、因果、并列、类比四种关系挤在一口气里，五个独立命题各自开口，
读的时候要同时挂着。

字数这个代理指标两头都不准：**太严**，禁掉了阮一峰 40% 的正常句子，把文字逼成电报（那
恰好是这个 prompt 最初要避免的毛病）；**也不够**，34 个字里照样塞得进「虽然 A，但 B，
因此 C」三条线。

所以规则改成 **一句话只走一条逻辑线**：顺着往下推（再、然后、于是、就）可以拉长；
转折加因果加并列混在一句就必须断开。prompt 里同时给了坏例和好例 —— 只给坏例，模型会
以为「长」本身有罪。字数降级成提醒：**过了 50 字回头检查一遍是不是掺了第二条线**，
是就断开，不是就留着。

顺带一个发现：**每段 90 字的硬上限已经物理排除了那个 92 字长句**（92 > 90）。剩下的
风险是 85 字的单句独段，而治它的是逻辑线规则，不是更紧的字数。

改完实测，分布落进了阮一峰的范围而不是被压在下面：

```
                  平均    中位   最长   >35 字   >50 字
阮一峰             34.2    34     71     40%      13%
改前（35 字上限）    —      —      63     25%       —
改后（逻辑线）      30.4    30     72     21%       9%
```

**每段 90 字仍然是唯一的硬约束**，它才是可读性的真正来源。模型基本守得住，但不是绝对：
加了收尾段之后的一轮实测里，18 段有 1 段写到 100 字。11% 的超幅不至于把段落变回那种
单句长段，所以没有在代码里做强制切分 —— 按句号切开听起来简单，实际很容易切出一个
三个字的孤儿段落，比超 10 个字更难看。

### 每篇结尾固定一个收尾段

前面几段讲「发生了什么」，最后一段讲「所以呢」：作者的判断落在哪里、读者该记住什么、
接下来会怎样、或者该怎么做。原先这一段时有时无 —— 有的篇子最后一段是真结论，有的就是
把最后一个要点讲完就停了。

写这条规则要同时防两个陷阱，两个都是「加个总结」的自然产物：

- **不许复述。** 论点那句已经印在正文上方，读者刚看过，收尾再说一遍等于白费一段
  （而一段是 90 字，占总额度的 15%）。
- **不许清嗓子。** 「总之」「综上所述」「这篇文章讨论了」都被明确禁掉。

文章本身没有结论时（链接汇总、发布公告），收尾要写清它为什么给不出结论，而不是硬凑。
实测出来的效果：

```
收尾（Antigravity 对比评测）
  所以结论不是本地模型不行，而是取舍不同。如果你在乎文件夹的长期整洁，
  愿意多等几秒的工具更合适；图快的话，Qwen 也够用。

收尾（Marginal Revolution 周五链接汇总）
  每个标题背后都可能有重要内容，但读者必须自己点开才能知道。
  这篇本身不提供可带走的东西，它只是周五的杂货铺。
```

第一条给出了论点里没有的判断（取舍而非优劣），第二条老实交代自己没有结论 —— 两个都不是
论点的回声。

### 顺手修掉的一个漏：摘要在解释自己的评分

同一轮实测里发现，链接汇总那篇的最后一段写的是「**分数低是因为**它没有论点，只是一个
导航页」。打分标准是内部的，写进正文就露馅了 —— 读者看到的是一份日报，不该看见编辑
后台。prompt 里补了一条：**永远不要提分数、分类，或者这是一份日报的一部分。**

**每段 90 字这个数，在两次加长里都没动过，这是故意的。** 总长 300 → 420 → 600，
每段一直是 90。加长买到的是**更多段**，不是更长的段 —— 节奏就挂在这个数上，
为「保持比例」把它一起放大，等于把那个 92 字的单句长段请回来。

`SummaryText` 里 `background` / `points` / `implication` 三个字段保留但已废弃，
只为让归档中的旧 digest 仍能渲染。

### 一次请求一篇文章

`BATCH_SIZE = 1`，从最初的 8 一路降下来的。

见过的所有畸形 JSON 都是**长回复里的结构性失误**：数组用 `}` 闭合、wrapper 在第一条
之后就关掉、少一个括号、写到一半被截断。它们随「模型要同时维持多少 JSON」增长，
按坏法逐个打补丁是输的 —— 补到第七种还在出新的。一篇文章的回复只有 ~300 字符、
一层嵌套，那是**另一个可靠性区间**，不是同一件事的小号版本。

代价是延迟和 system prompt 每篇重发一次，分别由 `REQUEST_CONCURRENCY`（默认 8，
`DAILY_CONCURRENCY` 可调）和 DeepSeek 的缓存命中价（$0.0028/M 对 $0.14/M）抵掉。
现在坏一次只损失一篇。

另外两个实测撞到的坑：

- **撞 `max_tokens` 被截断。** 上限 16000 是摘要还只有 45 字时定的；散文一批就写到
  30000 字符，截断后是非法 JSON，整批全灭。已提到 48000（模型支持 384k，这里不再是
  稀缺资源）。
- **静默少给。** 给 6 篇只返回 5 篇，**不报错**，JSON 完全合法只是短。所以每轮之后会
  检查哪些还缺（打分那轮看 `judged`，摘要那轮看有没有 thesis），
  **只针对缺口重新要一次**（`GAP_RETRIES = 2`）。

**SDK 超时必须压住**：`timeout: 60_000` + `maxRetries: 1`。原来是 180 秒 × 2 次重试，
一个卡住的请求能占着一个并发位 9 分钟 —— 实测整轮耗时在 28 秒和 10 分钟之间跳，
就是这个原因。

### 两轮调用，按「做什么」拆

① **只打分** → 用门槛筛掉一批 → ② **写摘要**（只写活下来的）。

打分先跑、单独跑，是为了**在写任何摘要之前就把不够格的丢掉**。实测 18 篇里 8 篇在
这里被拦下，一次摘要请求都没发出去 —— 摘要正是输出 token 的去处。打分那趟的回复只有
一个数字，30~70 字符。

代价是活下来的正文要发两次（打分一次、摘要一次），两轮 system prompt 不同，缓存前缀
没法共用。按 $0.14/M、每天约 42k 输入 token 算，大约每年一美元，不构成继续给没人读的
文章写摘要的理由。

**这条缝后来变成了一个入口。** 两轮之间既然本来就有一个「已经打完分、还没花摘要的钱」的
状态，那它就可以落盘、被人改、再接着跑 —— 就是 `npm run score` / `npm run summary`，
见下面「分两步跑」。`lib/summarize.ts` 因此导出的是 `scoreAll()` 和
`summarizeSurvivors()` 两个函数，而不是一个 `summarize()`：**两轮现在可能在两个进程里
跑**，所以第二轮拿不到第一轮的内存对象，只能从当天的文件里用 `verdictsFrom()` 重建。

同样因为可能跨进程，**文章上限（`MAX_ARTICLES_PER_CALL`）两轮各自都要切一遍**。只在
第一轮切的话，第二轮会看到没打过分的文章，而其中来自 `alwaysPublish` 源的那些会被直接
写摘要 —— 正是上限存在的意义所在的反面。

### 英文那一半

**两种语言在同一次调用里，中文先写、英文从写好的中文来。** 不开第三轮。

> 早先「打分 + 中文 + 英文」一次要，结果是中文 10/10、英文 0/10，模型把每个对象的前几个
> 字段填完就停了 —— 但那是**一次请求带一批文章**的年代。`BATCH_SIZE` 是 1 之后，同一个
> 合并回复只有约 2900 字符，实测 10 篇全部两种语言齐全。**那条教训讲的是回复长度，不是
> 「语言不能合并」。**

上面这段是当初砍掉英文之前留下的，它现在就是恢复它的依据。合并而不是另起一轮，理由有三条：

- **两半不会各说一套。** 重开一轮读一遍正文，等于让同一篇文章被判断两次，`/zh` 和 `/en`
  的 og:description、poster 正文会互相打架。紧接着从中文写，这个问题不存在。
- 正文只发一次而不是两次。
- 两个 pass 的 system prompt 仍然逐字节固定，DeepSeek 的 cached prefix 不受影响。

**英文不重试。** gap 重试的判据仍然只看 `zh.thesis`：重问英文等于重问整条（一次请求写两种
语言），把已经拿回来的中文重新押上去换另一半 —— 中文是产品的脊梁，不值这个价。英文没回来
的那一篇就发中文版，`/en` 对它回落到中文。`report()` 里那个 `N/total with English`
是这件事**唯一的**警报，一天读到 3/14 就是英文站那天大半回落了，别处不会有任何提示。
真要升级也只是一行：把英文加进 summary pass 的 `missing` 判据。

**这次合并有一笔已经量过的代价：长度纪律会变差。** 上面「额度是口头约束」那节记着：
中英合并到一轮之后 9/10 的篇目超出自己的额度，单独跑中文那一轮时低得多。**恢复英文就是
把这笔代价一起收回来**，心里要有数。

`renderArticle` 里那行预算跟着写明了「中文正文最多 N 字（英文不计入）」而不是「正文最多
N 字」—— 但**它不是解药**，同一节记着实测：加这个限定词把超额从 9/10 挪到 8/10，等于没动。
写它的理由只是「两种语言同一份回复、预算没说是给谁的」这个含糊是真的，不是它能换来纪律。

英文自己不给数字，长度靠结构钉住（段落断点和小标题数量照中文走）—— 那是模型能自查的规则，
而多一个字数预算只是多一个会被突破的软约束。

**英文那一节要求的是本地化而不是翻译。** 中文那半是「高中历史老师」的口吻，带 拼团／C位／
KPI；直译过去英文读者读到的是 group-buying 和 the C position。`SUMMARY_EXAMPLE` 里两半
都是手写的，英文那半额外担一件事：把「重新本地化」这条软规则**示范**出来（拼团 → neighbours
chipping in，C 位 → centre stage，KPI 照留）。这么软的规则，被模仿的概率远高于被遵守。

两半的段落数和小标题数逐块对齐 —— 例子里是 13 块 3 个小标题，两边都是。

现在回复比英文在的时候小了一半又装回一半，而这个文件里每一种畸形 JSON 都是随回复体积放大的。

**打分独立成一轮有一个已知代价**：`score` 成了模型对这篇文章产出的唯一一个 token，
前面没有摘要垫着。曾经把 `score` 放在摘要之后生成，实测把一篇评论汇总从 55 压到 28。
现在放弃了这个结构，实测分数仍然守住了（评论汇总 35、书单 24、闲聊帖 12，分布 12~72
不再挤在中段），推测是因为这一轮的 system prompt 只剩打分规则，没有一整套写作规则
在旁边分散注意力。**如果分数哪天又挤回中段，下一步是让这一轮开 thinking** —— 它的
回复足够小，不至于触发下面那个空回复故障。

### 改 prompt 之前先读这一节

prompt 现在是两份：`SCORE_SYSTEM`（角色 + 打分三问）和 `SUMMARY_SYSTEM`（分五节：
返回什么、格式硬要求、标题、英文、分类）。下面这段实测是在两者还合成一份
`ZH_SYSTEM` 的时候做的，结论对两份都成立。

它看起来啰嗦、重复、可以压缩。**那些重复是承重的。** 每一条都是某次故障留下的，
压掉就会把故障放回来。曾经把它从 4622 字符压到 2578，A/B 立刻显示：

| | 压缩前 | 压缩后 |
|---|---|---|
| 段落超字数 | 1/35 | **14/38** |
| 条目超上限 | 5/14 | 9/14 |
| 打分均值 | 52 | 61（明显变松） |

三处删掉的东西各自对应一个具体后果：

- **每段字数限制原本说两遍**（字段说明里一次、长度块里一次），还带
  `Not "about" — at most`。合并成一句流畅的话，模型就不当回事了。
- **「能被复述成『X 发生了』就是新闻」是可操作的判据**，不是修辞。删掉后打分普涨 9 分。
- **一个冒号的位置能决定输出长度。** 字段说明写成
  `2 or 3 paragraphs, each AT MOST 120 characters: the context, the evidence, what follows`
  时，冒号后三个并列项被读成「三段各写一项」，每篇段落数从 2.4 涨到 2.7 —— 而
  3 段 × 120 字上限 = 360，本来就超 300。改回 `Together they carry…` 立刻回到 2.5。

现在的版本是 3164 字符（发出去 1445 tokens，比原来省 17%），各项指标与原版持平、
段落合规更好。**方法比结论重要**：单轮 A/B 不可信 —— 同一份 prompt 连跑 6 轮，
「超上限篇数」在 2~5 之间飘、均分在 52~59 之间飘。要 n≥2 稳定复现才算数。
`scripts/` 里没留这个 A/B 脚本，重做时记住一点：**两份 prompt 必须跑同一批文章**。

## 版面：全部出卡片

**没有折叠，没有一行的降级档，没有源配额。** 过了 `publishMinScore` 的文章，每一篇都拿
一张完整卡片：封面、标题、一句话论点、正文。分类内按分数排序，栏内不设数量上限。

**版面上不再有任何取舍**，取舍全部前移到了 job 里那一道门槛。以前是三层结构 ——
不发布 / 一行 / 卡片 —— 三层意味着三个可调的地方，而中间那层的存在理由（「什么都不丢，
所以重的一天要能压缩」）在门槛接管之后就没了。**能上页面的就值得那张卡片的篇幅。**

删掉的东西：`ArticleRow` 组件、`.rows` / `.row*` 样式、`categories[].cardCount`、
`minScore`。默认落地的 tab 也随之简化 —— 原来要找「第一个真正有卡片的分类」，因为
某栏可能整栏都是低分行，打开就是一列光秃秃的链接；现在低分的根本不在页面上，
存在的栏必然有卡片，直接取第一个。

再往前一版还有个底部的「其余更新」折叠栏，早就删了；`Digest.folded` 字段保留但永远
为空 —— 归档里的旧 digest 仍带着数据，页面照常渲染它们。

源配额（原来 HN 3、Marginal Revolution 2）**已全部删除**。当时加它是因为纯按分数排序时
HN 靠数量霸榜；现在分类本身就限制了每栏的卡片数，高产源最多在自己那栏占 3 张卡，
其余自动降为行。

`Digest.folded` 字段保留但永远为空 —— 归档里的旧 digest 仍带着数据，页面照常渲染它们。

## 没有跨天去重，所以窗口必须严丝合缝

刻意的设计：**没有任何「已读」状态**，窗口就是过滤器。一次运行内部仍然按 URL 去重，
因为 XDA 两个分类 feed 会有重叠文章；跨天则完全不比。

这个设计有一个前提：**相邻两期的窗口必须首尾相接**。不接上就两头出错 —— 重叠会重复发，
留缝会永久丢。

### 窗口锚在钟点上，不是锚在运行时刻上

窗口曾经是 `[now - 24h, now]`，从运行的那一刻往回量。只有当每次运行都正好隔 24 小时时，
它才能完美平铺。`0 7 * * *` 的 cron 满足这个条件，`npm run once` 不满足 —— 而线上的
digest 记录了违反它的后果：

```
date         生成时刻(UTC)   窗口
2026-08-13   00:27:12       08-13T00:27 → 08-14T00:27
2026-08-14   20:45:17       08-13T20:45 → 08-14T20:45   ← 钟点上提前了 3.7 小时
```

两次运行间隔 20.3 小时，窗口重叠 3.7 小时，那段时间里发布的 4 篇文章被发了两次。
同一批数据里还有反方向的一例：08-11 和 08-12 两次运行间隔 25.2 小时，中间留了
1.2 小时的缝，那段时间的文章**一篇都没发过，也永远不会发**。重复是看得见的那一半，
静默丢失是更糟的那一半。

现在窗口是**固定的每日时段**：`前一天 07:00 → 当天 07:00`（`DAILY_TZ` 时区，锚点小时由
`DAILY_WINDOW_ANCHOR_HOUR` 决定，应与 `DAILY_CRON` 的小时一致）。同一天 8 点跑、9 点跑、
下午跑，窗口完全相同，结果也就完全相同。

在锚点之前跑（比如 LA 06:00）时 `to` 会夹到「现在」—— 还没发生的时间不能算覆盖过。
锚点之后重跑会补全那一天，写 digest 对同一个日期是幂等的。

### `from` 是「上一个锚点」，不是「锚点减 24 小时」

这两者一年里有两天不同，而那个不同就是同一个 bug 换了个地方：11 月夏令时结束那天，
前后两个 07:00 之间隔着 **25 个真实小时**，减 24 会落在 08:00，把一小时的文章丢进缝里。
所以两端都锚在墙上时钟，换季那两天的窗口自然是 23 或 25 小时 —— 这是对的，它正好覆盖
一个 07:00 到下一个 07:00 之间的全部时间。

`DAILY_WINDOW_DAYS`（默认 1）也因此以**天**为单位而不是小时：以小时计的窗口跨不过夏令时。

实测：连续 400 天逐日检查，0 重叠 0 缝隙，时长分布 `24h×398, 23h×1, 25h×1`。

## 摘要模型：DeepSeek

用 `deepseek-v4-flash`。DeepSeek 提供的是 **OpenAI 兼容接口**，所以代码里装的是
官方 `openai` SDK，只把 `baseURL` 指到 `https://api.deepseek.com` —— 换回别的
OpenAI 兼容服务商只需要改 `DEEPSEEK_BASE_URL` 和 `DAILY_MODEL`，代码不用动。

| | `deepseek-v4-flash` |
|---|---|
| 上下文 | 1M tokens |
| 最大输出 | 384K tokens |
| 输入 | $0.14 / 1M tokens |
| 输出 | $0.28 / 1M tokens |
| 缓存命中输入 | $0.0028 / 1M tokens |

按每天 ~10 篇全文（十几万 input tokens）算，成本在每天几分钱的量级。上下文和输出
上限都远大于我们的用量，所以 `MAX_ARTICLES_PER_CALL`（30）纯粹是防某个源突然
灌量的保险，不是 token 限制。

**相关文档**

- [DeepSeek API 文档首页 / 第一次调用](https://api-docs.deepseek.com/) —— base URL、OpenAI SDK 配置
- [Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing) —— 型号列表与计价
- [JSON Mode](https://api-docs.deepseek.com/guides/json_mode) —— 当前用的输出模式
- [Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/) —— v4 默认开，这里显式关掉
- [Tool Calls 指南](https://api-docs.deepseek.com/guides/tool_calls) —— 已弃用，见下节
- [API Keys 控制台](https://platform.deepseek.com/api_keys) —— 申请 key

**思考模式要显式关掉，而且不只是为了省钱。** v4 系列默认以 `high` effort 跑 thinking，
thinking token 按 output 计费。真正的问题是**它和 `json_object` 合不来**：为了改善打分
把它打开之后，15 篇里 4 篇丢了摘要，复现时 8 次调用有 5 次返回**空的 content**（62%）。
DeepSeek 文档承认 JSON mode「偶尔」返回空 content —— thinking 把「偶尔」变成了六成。
不是截断（`finish_reason` 从没是过 `length`），也不是超时（失败的是 1~7 分钟的短文，
74 分钟那篇反而成功）。请求里带
`thinking: {type: "disabled"}`，且**只发给 DeepSeek**（这是它特有的参数，
`isDeepSeek()` 判断 host）。早期没关时报过
`400 Thinking mode does not support this tool_choice`。

### 用 JSON mode，不用 tool call

请求带 `response_format: {"type":"json_object"}`，模型的回复走 `content` 字段。

**换掉 tool call 是因为 DeepSeek 的 tool-call `arguments` 会返回非法 JSON** ——
实测约每 5 次坏 1 次，而且坏法有四种，全是括号层面的：

```
丢闭合花括号   …"zh_points": ["…"], {"index": 1, …
缺开方括号     "zh_points": "A", "B"]
闭合符类型错   "zh_points": ["…", "…"}]}
未转义双引号   "zh_thesis": "他说"你好"世界"
```

这些不像模型生成正文时会犯的错，更像序列化/分片拼装的问题，而且上游有未关闭的
同类 issue。走 `content` 绕开了那条路径。

JSON mode 有自己的要求，三条都满足了：prompt 里必须出现 "json"、必须给格式样例、
`max_tokens` 要够大以免截断。官方还提示**可能返回空 content**，所以 `extractRows()`
会显式检查并报错。

**user message 里那句 `Reply with json only` 不能删。** 官方明确写着：不在 system 或 user
消息里显式要求生成 JSON 的话，「模型可能生成不断的空白字符直到达到 token 上限」。
我们的 `max_tokens` 是 48000 —— 真触发就是为一坨空格付 48k output token，还要卡满
整个超时。system prompt 里只有大写的 `JSON`，那句小写的 `json` 在 user message 里，
是唯一确定满足要求的地方。

DeepSeek **不支持 `json_schema`**（`response_format` 只有 `text` 和 `json_object`），
所以上面那条 enum 的代价没有办法绕过，只能靠 prompt 文字 + `resolveCategory()` 兜底。

**代价**：分类的 `enum` 强制没有了 —— tool schema 能约束取值，prompt 文字不能。
所以分类边界、打分标准、字数限制全部移进了 system prompt，`resolveCategory()` 兜底把
未知值归到 fallback 分类。

无效分类是**低频但真实**的：一次 prompt 压缩里删掉了
`Never invent a value outside the list.` 这句，A/B 立刻出现 1/14 的编造值；加回去之后
连续 4 轮 56 篇全部合法。所以那句不是废话，`resolveCategory()` 的兜底也不是摆设。

曾经有一层约 130 行的抢救代码，按 `{"index"` 切分再逐个补齐括号，能从坏 JSON 里救回
大部分文章。**切到 JSON mode 后删掉了** —— 那是为 tool-call 的坏法写的。风险是坏一次
就整批退化成纯标题；`logParseFailure()` 保留着，出错时打印出错位置前后 120 字符，
那是判断新坏法的唯一线索。

### 分两步跑：改完分数再生成摘要

`npm run once` 里那两轮模型调用可以拆开跑，中间停下来让人改分数：

```bash
npm run score                        # 抓取 + 只打分，写进当天的 digest 文件，然后停
vim data/repo/daily/2026/08/2026-08-24.json   # 改 articles[].score
npm run summary -- --date=2026-08-24 # 按改后的分数写摘要 + commit + push
```

`npm run summary` 不带 `--date` 就是今天（按 `DAILY_TZ`）。

**没有中间文件，改的就是当天那份 digest。** 两个命令各自只写自己那几个字段：

| | 写 | 不碰 |
|---|---|---|
| `npm run score` | `score`、`modelScore`、`review` | `summary`、`category`、`titleZh` |
| `npm run summary` | `summary`、`category`、`titleZh` | `score`、`modelScore`、`review` |

所以在一份已经有摘要的日子上重跑 `score`，摘要原样留着，只有分数被刷新；反过来
`summary` 也永远不会把你改的分数改回去。**但重跑 `score` 会覆盖你改过的分数** ——
`score` 就是它的字段。没有合并逻辑，因为合并必须决定「新的模型分」和「你的覆盖」谁赢，
而这个答案取决于你当初为什么要覆盖。

`score` 写出来的那份文件和发布出去的那份有两处不同，都是临时的：

- **全部文章都在 `articles` 里**，包括线下的 —— 因为「把分数改上去」必须能把一篇捞上来。
  门槛是 `summary` 才应用的，它负责把没过线的挪进 `rejected`。
- **每篇带着 `body`（正文）**。摘要那一轮要用；换成届时重抓的话，摘出来的就不是当初打分的
  那段文字了 —— HN 指向的第三方页面隔几小时就可能消失。`summary` 写发布版时不带 `body`，
  所以正文从不进 git。

几件要知道的：

- **`score` 不 commit 也不 push**，写完文件就停，clone 里留着一份 dirty 的改动 —— 那正是
  你要打开编辑的东西。
- **`summary` 先读文件、后 `ensureRepo()`**，和这里所有别的路径顺序相反，是故意的：你改的
  分数是未提交的工作区改动，而同步在没有本地提交可保时会 `git reset --hard origin/…`。
  先读进内存，重置就冲不掉它了。
- **`summary` 认不出已经发布过的日子**：发布版不带 `body`，它据此报错说「这天已经完成或
  从未打分」，让你重新 `npm run score`，而不是默默去抓一份新的 —— 后者会浪费掉那次编辑。
- **`npm run once` 不写中间态**，两轮在内存里连着跑，落盘的只有发布版。定时任务半路停下
  留一个脏 clone 和一份写了一半的当天数据，比它要恢复的那个故障更糟。
- **改过的分数会写进 digest 留痕**：`modelScore`（模型原分）和 `scoredBy: "human"`，只在
  两个数不一致时写。被你压到线下的文章同样会带 —— `rejected` 里能分辨「模型否掉的」和
  「人否掉的」，否则那份列表就失去了它唯一的用处。
- **`review` 不会跟着改。** 你把分数从 28 改到 34，note 里还写着 substance 5 / surprise 5。
  这是故意的：note 是模型说过的话，改它等于伪造证词；而 `modelScore` 就在旁边，两个数
  对不上正是「这里有人干预过」的信号。
- **过了线却没有摘要的文章不会发布**（模型重试完仍然失败的那种），日志里会单独报出来 ——
  空卡片比少一张卡片糟。

**为什么值得有这一步。** 门槛是 30，量纲是 5~50，五个维度各 1~10 —— 任何一维抖 1 分就能
让一篇文章翻面，而同一篇文章两次打分的方差能到 ±20（见上面那一节）。在此之前，想让一篇
28 分的文章发出来，唯一的办法是改判据再把整天重跑一遍：一件为了一篇文章而做、却会移动
当天所有分数的事。现在改一个数字就行，而且**门槛是在写任何摘要之前应用的**，所以把一篇
文章调过线只花它自己那一次摘要的钱，不是一整天的钱。

**远端地址是推导出来的，不用配**：

1. 设了 `GIT_REMOTE` → 原样使用
2. 否则设了 `GIT_TOKEN` → HTTPS + token（**容器走这条**，它没有 SSH key）
3. 否则 → `git@github.com:<GIT_REPO>.git`，用你本机已加载的 SSH key

顺序不是随意的：直接把 SSH 设成默认值会更简单，但会让每次部署都挂。

push 失败不致命 —— 内容已 commit 在本地，下次运行走 rebase 而非 hard reset，
会被一并带上去。认证类错误（`Repository not found`、`Permission denied` 等）
不会重试，2 秒内失败，而不是白等 65 秒退避。

起网站（读上面那次跑出来的数据）：

```bash
npm run dev
```

`apps/daily/data/`，容器里 WORKDIR 是 `/app`，所以是 `/app/data/` —— compose 的卷

## 站点自己的 feed

这个站抓 69 个 RSS 源，自己也出一份 —— `src/lib/feed.ts` 生成 Atom，两个路由发出去：

```
/feed.xml          按 Accept-Language 302 到下面两个之一
/zh/feed.xml       每日干货
/en/feed.xml       Daily Takes
```

几个当时定下来的取舍：

- **entry 里放整篇摘要，不是导语加链接。** 整个 app 的前提是「这份摘要替代读原文」，
  一个只给标题和链接的 feed 会把这个前提反过来 —— 读者又回到开一堆标签页，而唯一
  为他写的那段文字恰好是 feed 里没有的。代价只是 XML 体积（实测中文 50KB / 英文 98KB
  装 37 条），是这里最便宜的东西。
- **Atom 而不是 RSS 2.0**，为了三样 RSS 没有正经位置放的东西：不等于链接的稳定
  `<id>`、和 `<published>` 分开的 `<updated>`（原文发表时间 vs. 我们写下这份摘要的
  时间，读者拿它们做的是两件事），以及 `xml:lang` —— 这个站把 /zh 和 /en 当两份刊物。
- **一种语言一份 feed**，和隔壁 manifest 同一条理由：一份混合 feed 会把每篇文章的
  两个语言版本都塞进去，而没有任何阅读器能只显示其中一个。
- **窗口是 7 天、上限 100 条。** README 前面那条给别人家 feed 定的规矩
  （`feed 条数 ÷ 日产量 > 1 天`）反过来也约束自己：周poll 的阅读器、停机几天的容器，
  都得能找回没见过的条目。
- **`/feed.xml` 是 302 协商，不是另发一份。** 未加语言前缀的路径由 `proxy.ts` 协商，
  sitemap 的 x-default 也是这么说的；同一个问题有两套行为就多了一套。而且它不能省 ——
  proxy 的 matcher 跳过带扩展名的路径，没有这个 handler `/feed.xml` 是 404。
- **`<link rel="alternate" type="application/atom+xml">` 在 `layout.tsx` 的
  metadata 里**，只声明当前语言那一份。没有它，读者拿到域名找不到订阅地址。

## 输出的 JSON

`daily/<yyyy>/<mm>/<yyyy-mm-dd>.json`，公开可读：

```
https://raw.githubusercontent.com/imnaifu/files/main/daily/2026/08/2026-08-10.json
```

字段定义在 `src/lib/types.ts` —— 那是写入方和页面共用的契约，首份 digest 发出去
之后只能加字段，不要改已有字段的含义。

`articles` 是页面渲染的那批；`rejected` 是低于 `publishMinScore` 被丢掉的那批，只有
标题／链接／源／分数，**页面不读它**，纯粹留作事后审查。它是可选字段，因为它出现
之前写的归档 digest 没有这一项。

`summary.en` 同样是可选字段，同样的道理 —— 而且它比 `rejected` 多一种缺失方式：某一跑
里中文回来了、英文没回来，那一篇就只有 `zh`。**判断有没有英文只能看字段在不在**，不要
拿空字符串当信号（写入方从不写空的那一半）。

## 页面

- `/` 今天（截图目标）。当天还没跑时回退显示磁盘上最新的一天
- `/d/2026-08-10` 单日固定链接
- `/archive` 归档列表，直接扫 clone 目录得出，没有索引文件
- `/feed.xml`、`/zh/feed.xml`、`/en/feed.xml` Atom 输出，见上面「站点自己的 feed」

每条路径都带语言前缀（`/zh/…`、`/en/…`），**两种语言渲染的是各自的摘要**。取哪一份由
`summaryFor`（`lib/take.ts`）一处决定，poster 和 og:description 也走它 —— 所以
`/en/d/…/share.png` 是英文长图，分页数按英文正文自己算（`jobs/posters.ts` 预热时也是
按语言分别算的，两半的图片张数可以不一样）。

`inLanguage` 那个 JSON-LD 字段说的是**这一页正文的语言**，不是外壳的：`/en` 拿到英文
摘要就是 `en-US`，回落到中文就还是 `zh-CN` —— 在中文正文上宣称 `en-US` 是同一个谎的
另一个方向。

### 报头的副标题：从页脚搬上来的那一句

`t.tagline`（`lib/i18n.ts`）**同时是五样东西**：报头的第二行、每一页的 meta description、
manifest 的 `description`、Atom feed 的 `<subtitle>`，以及分享海报底部那行（`lib/og.tsx`）。
所以它只能有一句，改它要一起考虑这五个位置。

**它原来在页脚。** 一条横线下面、12px 的灰字、排在读者已经决定不再往下看的所有东西后面 ——
那是 fine print 的位置，而它是这个站关于自己的**唯一**一句主张。搬到报头之后它是页面上
仅次于字标的第二样东西；更重要的是单篇文章页：从分享链接进来的读者，第一次知道自己落在
哪里就是靠这一行。页脚现在只剩名字、回 lab115.com 的链接和版权 —— 那些本来就是 fine print。

`Masthead` 的 `subtitle` 这个 prop **一直存在但很久没人传**（它原本是给「每日干货 / Daily
Takes」这种双语孪生标题用的，被「一次只出一种语言」的规矩废掉了）。现在四种页面全都传。

文案现在是「**快速读完各个领域专家的最新观点。**」，三个词各有各的账：

- `各个领域` —— `config.json` 的分类是 技术/商业/投资/经济/科学/设计/生活/人文，撑得住
- `专家` —— 靠的是源全是署名博客、作者本人在做那件事（心内科医生、估值教授、流行病学家、
  写自己系统的工程师）。**收一个通讯社或聚合站就会让这句话变成假的**，这比 README 上面
  任何一条理由都更硬
- `快速` —— 这里唯一一个关于读者时间的承诺
- **`每天` 去掉了**，因为它正上方的字标就是「每日干货 / Daily Takes」，节奏已经说过一遍，
  副标题只有一句话的额度不该花在读者刚读过的词上

两个连带的版式改动，都在 `components/Shell.tsx`：

- **字号按有没有副标题分档，图标尺寸不动。** 规则是「标题 + 副标题的高度不超过图标」，
  而满足它有两个方向：把图标撑大，或者把字缩小。**撑大那条路走过并且退掉了** —— 要盖住
  英文副标题在窄屏折成两行的 85px，图标得做到 88px 见方，那时它就不是在引出字标，而是在
  跟字标抢地方。现在走缩字：有副标题时标题是 `text-2xl sm:text-3xl` 且 `leading-none`
  （让出行距是最后几个像素的来源，而一个两到四字的字标是唯一付得起这个代价的字符串），
  副标题 `text-xs sm:text-sm`。浏览器实测（文字高 / 图标高）：手机 44/44，`sm:` 及以上
  54/56，中英文都一样。**手机那一列是刚好填满的**，往任何一行加东西都得从另一行扣。
- **别指望 CSS 让图标「跟着文字高度长」。** `self-stretch` + `aspect-square` 的 `<img>`
  没有确定宽度：宽度来自行高、行高来自文字高、文字高来自剩下的宽度。浏览器不报错，它会把
  这个循环解出来 —— 实测解成 **694px 见方**，字标被挤成 47px 一列。`object-contain` 也
  救不了：盒子会被拉伸，但方形的画面只按盒子**宽度**渲染，可见的图标一点没变高。
- **英文 tagline 必须一行放得下**，这是长度限制不是排版偏好：12px 下它要 264px，360px 的
  手机正好给 264px。低于 340px 视口会折行、把文字块撑过图标 —— 这个取舍是认的，今天在售的
  手机没有那么窄，而为它们缩短这句会让所有不那么窄的手机都损失掉这句话的主张。
- **副标题不再用 `italic`**，见上面字体那一节。

设计取自 Uizard 的 "Readium" 读书 App 模板：奶油底 `#FBF3E9`、深靛蓝 `#3B3563`、
暖橙 `#EFA050`、卡片米色 `#F3E8D8`，页头有机色块 + 书封网格。
版心固定 750px 竖版，为整页截图设计，不依赖任何 hover 效果。
颜色和字体都在 `src/index.css` 顶部的 `:root` 里。

**样式用 Tailwind v4**（CSS-first，没有 `tailwind.config.js`）。

`index.css` 从 730 行降到 62 行，而且**一个选择器都没有** —— 只剩 `@theme` 的 token
（颜色、字体栈、`max-w-page`、`rounded-card`、`rounded-blob`、两个阴影）和一条
`:root { color-scheme: light }`。其余全部在组件的 `className` 上。

**移动优先，用原生 `sm:`。** 早先一版为了「什么都不动」保留了原来「桌面为基准、窄屏覆盖」
的结构，为此声明了一个 `@custom-variant narrow (@media (max-width: 560px))`，每个响应式
值都要写两遍。现在断点就是 Tailwind 的 `sm`（40rem），裸类是手机、`sm:` 打开桌面。

**页头的两个有机色块是真的 div，不是伪元素。** 作为伪元素它们必须在样式表里有个类，
而那个类存在的唯一理由就是放这两组偏移量；挪进 JSX 后 `@layer components` 整层可以删掉。
八值的 `border-radius` 收成了 `--radius-blob` token，所以用起来就是 `rounded-blob`。

**跨页复用的是组件，不是 class 字符串。** 归档页和日报页共用同一个 `<Masthead>` /
`<PageShell>` / `<Footer>` / `<SectionHead>`（都在 `src/components/Shell.tsx`）。中间有一版
是导出七个 class 名字符串加一个 `styles.ts`，那是两个页面共用外观但不共用组件的产物 ——
现在字符串没了，只剩 `PAD` 和 `SECTION` 两个。

**`+` 兄弟选择器换成了容器属性**：`.card + .card` 的间距变成 section 上的
`flex flex-col gap-3`（顺带把标题的下边距也一起管了），折叠列表的分隔线变成
`divide-y divide-line`。

**只剩 3 个 arbitrary 值**：两处 `leading-[1.85]` 和一个 `size-[3px]` 的圆点。字号从 14 种
（`text-[13.5px]` `text-[14.5px]` `text-[17.5px]` …）塌成 6 级标准刻度。

`leading-[1.85]` 是故意留的：摘要是按「读」而不是「扫」重写的，Tailwind 最近的一档
`leading-relaxed`（1.625）会把那次改动争到的空气收回去一部分。

**字体：整页一套无衬线** —— 中文思源黑体（Noto Sans SC，就是 Adobe 的 Source Han
Sans），英文 Manrope。模板原本的粗衬线标题（Bitter + 思源宋体）已经拿掉了。

这不只是把变量指向换个值。原来的层级是**靠字面**做的：标题衬线、正文无衬线，所以
`.summary--hero .summary__thesis` 用 `font-weight: 400` 也能从周围正文里跳出来。全部
变成无衬线之后，「只是稍微大一点」不再是信号，那一处要改成 600 才站得住 —— 一次
find-replace 会静默把它拍平。

两个连带的点：

- **`Noto Sans SC` 的 600 字重是这次才请求的。** `.summary__thesis` 一直写着
  `font-weight: 600`，但字体 URL 只加载了 400/500/700，中文那一档长期是浏览器凑的。
  现在字重是区分论点和正文的**唯一**手段，真字面必须在。
- **Manrope 和思源黑体在 Google Fonts 上都没有斜体轴**，而 `.masthead__title small`
  （Daily Takes）和 `.section__sub`（英文栏目名）还在要斜体 —— 这两行现在是合成倾斜。
  次要文字上可以接受；真觉得不对，就去掉 `font-style: italic`，它们本来还有字号和
  颜色在区分。原来 Bitter 有真斜体（URL 里的 `1,500` 就是为它加载的）。

  **后来去掉了，两处都是。** 报头第二行改成放 tagline（见下面「报头的副标题」）之后，
  它承载的从一个短标题变成了一整句中文，而合成倾斜是把直立的汉字整体切斜 —— 短标题上
  看不出来，18px 的一整句上非常明显。现在全站没有任何一处 `italic`。

顺带少下载两套字体，对一个「打开就截图」的页面是净收益。

- **正文用 `font-medium`（500），不是默认的 400。** 中文每个字的笔画密度远高于拉丁文，
  同一个字重在英文里正常、在中文里就显得发虚 —— 14px 的 400 尤其明显。500 的中文子集在
  字体 URL 里（`400;500;600;700`），所以这是真字面，不是浏览器合成的伪粗体（验证方式：
  `document.fonts.check('500 14px "Noto Sans SC"', "正文")` 为 true，且该字重有 17/101
  个子集实际下载）。副产物：改完之后整页已经没有中文用 400 了。

### 简化是拿视觉保真度换的，这笔账要记清

第一版转换的目标是「零视觉差异」，并且做到了 —— 改前改后各打一份 computed style 快照
（首页 223 个元素、归档页 33 个，含伪元素和盒子尺寸）做 diff，总高度 5482px 一致、
DOM 路径全同、真实差异 0 种。代价是满屏的 `text-[13.5px]` / `mt-[34px]` / `py-[7px]`，
一个自定义断点变体，和一条压回 Tailwind 默认行高的 `html { line-height: normal }`。

后来明确不要求一模一样，于是全部换成标准刻度。**现在的页面和最初有肉眼可见的小差别**，
都是刻度取整的结果：

| | 原来 | 现在 |
|---|---|---|
| 报头字号 | 54 / 40px | `text-5xl` / `text-4xl`（48 / 36px） |
| 正文字号 | 13.5px | `text-sm`（14px） |
| 段间距 | 11px | `gap-3`（12px） |
| 卡片内边距 | 16px、22px | `p-4`、`p-5`（16 / 20px） |
| 断点 | 560px | `sm` = 640px |
| 未声明处的行高 | `normal` | 1.5（Tailwind 默认，不再压制） |

色块位置反而是精确的 —— `-top-26 -left-21 h-50 w-65` 正好等于 -104 / -84 / 200 / 260px。

那两份快照脚本和 diff 工具没有留在仓库里，是一次性的验证。**如果哪天再动样式且要求保真，
重新写一遍比读旧脚本便宜。**

封面图的降级是纯 CSS 的：渐变色块（按来源配色 + 文章 id 决定角度）永远渲染在底层，
照片盖在上面。XDA 的 CDN 会间歇性超时，图挂了就自然露出渐变，不需要客户端 JS。
