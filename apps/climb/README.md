# climb

物理攀爬解谜的核心机制原型。拖动手脚抓岩点，靠重心转移和摆荡够到下一个点，体力耗尽就脱手坠落。

灵感来自 [Klifur](https://torfi.itch.io/klifur)（Torfi 作品，Unity 6.3 + 2D IK + Physics2D）。**这里的代码和美术全部从零实现**，没有使用原作的任何素材或代码——游戏机制不受版权保护，素材受。

```bash
npm install
npm run dev      # http://localhost:5180
npm run build    # 输出到 dist/，base 为相对路径，可直接丢进任意静态目录
```

## 技术选型

**PixiJS 8**（WebGL 批渲染 + Graphics 程序化几何 + federated 指针事件），物理和 IK 手写，**不用通用刚体引擎**。

理由：攀爬者本质上就是「几个被钉住的端点 + 一堆骨长约束 + 一个受重力的重心」，用 PBD（Position Based Dynamics）直接表达只需几十行，而且约束刚度就是手感旋钮。通用引擎的关节 solver 反而要和它自己那套 warm-start / baumgarte 参数打架。


## 物理模型

11 个质点：`pelvis / chest / head / shoulderL,R / hipL,R / handL,R / footL,R`。

- **躯干**是刚性桁架：骨架约束 + 交叉斜撑。只有链式约束的话躯干会像面条一样剪切变形。
- **四肢**各两条单向约束，对应真实肢体的两种受力：
  - `max`——拉不长。拉直后继续拖光标就会拽动躯干，这是「拖手换重心」的手感来源。
  - `min`——压不瘪。腿因此能当受压支柱把身体撑在脚点上。少了这条，重力会把髋部一路压到脚上、膝盖被 IK 甩出体外。
- **抓握**是硬锚点（`invMass = 0`）。每个抓握建立时都验证过肢体真的够得到，所以不会产生不可行的配置。
- **拖拽**是有限刚度的软约束（`Attachment`），**绝不能硬钉**。理由见下面第一条坑。
- **肘/膝不参与物理**，渲染时用解析 IK 从根部和末端反解。

## 三个容易踩的坑

**1. 被拖拽的末端绝不能钉死。** 如果拖拽时把末端设成 `invMass = 0`，它就是个**无限强的作动器**，永远赢过所有约束。于是形成棘轮：末端被钉在离根部 1.6 倍臂展处 → 根部被拽过去一点 → 下一帧钳制圈以新根部为圆心又能往外挪一点 → 身体被无限撑开，连躯干都会被拉成一条斜板。必须用有限刚度的软约束，让抓握点和躯干桁架能反抗它，系统才会落到真实平衡点。

配套结论：吸附判定要用**手/脚质点的真实位置**，不是光标位置。拖不动时手会落在光标后面，那时候它其实没够到，预览环也就不该亮——「够不到吸不上」于是由物理本身保证。`GRIP.snapReachTolerance` 只是兜底。

**2. 软约束要放在距离约束之前投影。** 软约束每次都会引入一点长度违反。放在后面的话，最后一轮迭代引入的违反再也没人纠正，实测残留 17% 的肢体拉伸；放在前面（每轮最后一步总是距离约束投影）降到 2%。

**3. 关卡几何被身体尺寸夹得很死。** 三条不变量，`level.ts` 里都有开发期自检——我在这上面连栽了三次，每次都是自检没覆盖到的那一条：

- 同一肢体单步距离 ≲ 0.85 × 臂展。不能按拉伸后的距离来设计。
- 手脚级差 × 单步距离（身体要跨越的**斜边**，不只是垂直距离）必须落在 `[身体最小跨度, 身体最大跨度]` 内。有横向漂移时特别容易踩：级差 4 × 步距 52 = 208 已经超过最大跨度 186，起始姿势直接畸形。这条斜边长度还决定重力下的静态姿势：太短腿会被压到最小折叠、膝盖横甩成一根横杠。
- **目标点必须在最后一步的可达高度内。** 抓最高点时脚还踩在低 `HAND_FOOT_RUNG_GAP` 级，「腿最长 + 躯干刚性」一起卡死了肩膀能升到的最高位置，从而卡死手能够到的最高点。目标点高 6px 就够不到。

顺带一个设计层面的取舍：**线路斜度和自然姿势直接矛盾**。斜度越大，领先侧两条肢体顶到长度上限、另两条松着，姿势会变成很丑的「一字马」。这里选了自然姿势优先——线路收窄接近垂直，`levelView` 再把岩壁宽度从抓点范围推导出来、画成一根框住线路的石柱，让构图看起来是刻意的。

## 体力模型

刻意区分手和脚：踩住脚点省力，累的是把体重挂在手上。于是策略压力变成「先把脚放好，再动手」——正是真实攀爬的核心技巧。

双脚踩稳 + 至少一只手抓着 + 没在拖动 = 休息姿势，回体力。

## 开发调试

dev 构建会挂 `window.__climb`（生产构建中被剔除）：

```js
__climb.snapshot()        // 游戏状态 + 四肢抓握情况 + 髋部位置
__climb.advance(1/60)     // 手动推进一帧（后台标签页 rAF 被冻结时用）
__climb.resetLevel()
__climb.config            // { BODY, GRIP, PHYSICS, STAMINA }，运行时可改，不用刷新
__climb.climber / .level / .input
```

`config` 可以直接在控制台扫参数，例如比较不同拖拽刚度下的形变量：

```js
for (const s of [0.12, 0.35, 0.8]) { __climb.config.GRIP.dragStiffness = s; /* 跑一遍线路并测量 */ }
```

`advance()` 存在的原因：主循环和测试共用同一条推进路径，否则浏览器在后台标签页冻结 `requestAnimationFrame`，自动化里没法验证坠落/过关这些状态机转移。

## 第一版范围

已实现：四肢 IK 拖拽、重心摆荡、抓点吸附与落点预览、体力与休息、最后一个抓点的拾取保护、坠落自动重置、过关判定。

未实现（等手感定稿）：多关卡、星级/最优步数、存档、音效、美术资源。抓点的 `jug` / `crimp` 目前只有视觉差异，判定上不区分难度。
